# 25 검증 장치 수정: 통과가 실제로 무언가를 증명하게

## 배경과 목표
이 저장소는 커밋마다 테스트와 end-to-end를 돌리고, 그 결과를 근거로 피처를 병합한다. 그런데 [회고 리뷰](../reviews/2026-10-20-retrospective.md)에서 그 근거가 허술한 곳이 여럿 나왔다.
- ASan 잡의 UBSan은 미정의 동작을 찾아도 테스트를 실패시키지 않았다.
- 기본 end-to-end는 몬스터 하나만 봐도 "다른 플레이어를 봤다"로 세어, 입력이 전혀 처리되지 않아도 통과할 수 있었다.
- 사후 확인은 처치가 DB에 기록됐는지 보지 않았다. 이슈 013이 PASS 뒤에 숨은 이유다.

이 PR은 뒤의 수정 PR들을 더 엄격한 검사로 확인하려고, 그보다 먼저 검증 장치를 고친다. 완료 조건: 지적마다 코드로 확인하고 고치며, 새 확인이 실제로 결함을 잡는 것을 보인다.

## 고민한 선택지와 결정
| 주제 | 선택지 | 결정 |
|---|---|---|
| UBSan | 보고만 / 첫 발견에서 중단 | 중단(`-fno-sanitize-recover=all`). 켰을 때 숨어 있던 미정의 동작이 드러날 수 있었지만, 176개 테스트 모두 통과했다 |
| "만났다"의 기준 | 보이는 엔티티 아무거나 / 다른 플레이어만 | 다른 플레이어만. 몬스터나 아이템은 두 클라이언트가 같은 세계에 있다는 증거가 아니다 |
| 입장의 기준 | Welcome 수신 / Welcome과 입력 처리 | 입력 처리까지. 모든 봇의 이동 입력이 한 번 이상 Zone에 반영돼야 한다. Zone이 입력을 무시하면 봇이 같은 지점에서 태어나도 실패한다 |
| 처치 판정 | 봇이 본 처치 수 / DB의 처치 영수증 | 둘 다. 봇이 본 것은 Zone의 판정이고, DB는 확정이다. 스크립트가 이 실행 이후의 영수증을 센다 |
| 사후 세션 확인 범위 | DB 전체 / 이 실행의 계정·시각 | 이 실행만. 예전에 죽은 뷰어 세션 하나가 이후 모든 실행을 실패시키지 않게 한다 |
| 대량 봇의 티켓 | 모두 준비한 뒤 접속 / 계정 먼저, 티켓은 접속 직전 | 두 단계. 느린 부분(비밀번호 해시)이 끝난 뒤에 티켓을 받으니, 봇이 많아도 티켓이 30초 수명 안에 쓰인다 |
| 탐색(Probe) 단계 | 유지 / 제거 | 제거. 초기 이력에 CMake·솔루션 파일이 없던 시절의 흔적이고, 지금은 잡이 모든 단계를 건너뛰고 통과할 여지만 남긴다 |

## 구현
- `cmake/Sanitizers.cmake`: `-fno-sanitize-recover=all`. `CMakePresets.json` 테스트 프리셋: `noTestsAction: error`
- CI: 의존성 캐시 키에 컴파일러 버전(`g++-14 -dumpfullversion`). 도구 설치를 캐시 복원 앞으로 옮기고, C++ 잡은 의존성 잡의 출력으로 같은 키를 쓴다. 탐색 단계와 그 조건을 지웠다
- loadgen 판정: 다른 플레이어만 센 `max_visible_players`, 입력이 처리된 봇 수 `inputs_acked`, 보낸 시전 수 집계, "모름" 결과 집계
- 월드 모델: 입장 전 스냅샷, 서버 틱 역행, 다른 엔티티를 자기라고 부르는 스냅샷을 모순으로 센다. 대기·모름 결과는 거절로 세지 않는다
- loadgen 준비: 계정·캐릭터(1단계)와 입장 티켓(2단계)을 나눴다. Backend API를 둘로 나누고 ID를 강타입으로. 캐릭터 이름은 시드 난수의 13자리 16진수(`std::hash` 24비트에서 바꿈), 이름 생성은 프로필의 `IdentityOf`로 옮겨 테스트한다
- Fighter: 시전 간격을 밀리초로 두고, 관찰의 서버 틱 속도(`tick_hz`, Welcome의 `simulation_hz`)로 환산한다
- `scripts/e2e-local.sh`: 포트를 다른 스택이 쓰면 시작하지 않음, 프로세스를 띄우자마자 정리 목록에 넣음, 고정 대기 대신 준비 로그 대기, Zone 시드 고정, 이 실행으로 한정한 세션 확인, DB 처치 영수증 확인
- `scripts/dev-stack.sh`: 이미 떠 있으면 올리기 거부, 준비 로그 대기, 3초 안에 안 끝나면 강제 종료
- 계약: `RecordKillRequest`의 지운 필드 `gold = 8`을 `reserved`로. README의 JSON ID 설명을 실제(숫자)에 맞춤
- 뷰어: 유실 슬라이더는 위치 표본만 버림(엔티티 집합은 항상 반영), 엔티티 종류를 계약 enum에서, 결과 상태를 계약 enum으로, 재입장 때 이전 연결을 조용히 닫음, 바닥 아이템을 보라 사각형으로
- 테스트 7개: 판정 2(입력 미처리, 몬스터만 본 봇), 월드 모델 3(플레이어만 만남, 대기·모름, 새 모순), Fighter 1(서버 틱 속도), 프로필 1(봇 이름)
- README 검증 절, 회고 리뷰 문서의 처리 결과

## 만난 문제
- 새 월드 모델 테스트가 처음에 실패했다. Welcome 전 스냅샷이 "입장 전 스냅샷"과 "자기 엔티티 불일치"로 두 번 세어졌다. 자기 엔티티 비교는 Welcome 뒤에만 하도록 고쳤다.
- clang-tidy가 `accounts[i]`를 검사한 뒤 다시 `*accounts[i]`로 꺼내는 코드를 "검사 없는 optional 접근"으로 막았다. 같은 참조로 검사하고 쓰게 고쳤다.

## 검증
- C++: dev 176개 통과(24보다 7개 늘었다), clang-tidy 경고 0, ASan·UBSan 176개 통과(이제 UBSan 발견이 테스트를 실패시킨다), 형식 검사 통과.
- .NET: 코드 변경 없음(계약 생성 코드만). 빌드 경고 0, 단위 4개·통합 33개 통과.
- 보호 장치: 대화형 스택이 떠 있을 때 `dev-stack.sh up`은 "이미 실행 중", `e2e-local.sh`는 "포트 5100 사용 중"으로 시작을 거부한다.
- 새 확인이 이슈 013을 잡는다:

## 남긴 것
- 이슈 013(재시작 직후 배정)은 다음 Backend 수정 PR에서 고친다. 그때까지 end-to-end를 연달아 돌리면 위처럼 FAIL이 나는 것이 맞다.
- CI에서 end-to-end를 돌리는 것은 Docker와 PostgreSQL이 필요해 뒤로 미룬다.
- 프로필과 뷰어에 복사된 스킬 번호·사거리, 계약의 "0 = 몬스터 공격" 같은 의미는 규칙 정리 PR에서 다룬다.

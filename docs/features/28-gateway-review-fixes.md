# 28 Gateway 리뷰 수정: 남지 않는 세션, 해제되지 않는 연결, 끝이 있는 기다림

## 배경과 목표
이 저장소는 먼저 만든 이력을 피처 단위로 다시 쌓으면서, 이미 옮긴 0~5단계 코드를 한 번 회고 리뷰했다([2026-10-20 회고 리뷰](../reviews/2026-10-20-retrospective.md)). 이 PR은 그중 Gateway와 C++ 공통 전송 계층 지적 G1~G9를 다룬다. Gateway는 클라이언트의 TCP·WebSocket 연결을 받아 입장 티켓을 Backend에 확인(Redeem)하고, 세션을 Zone에 붙여 입력과 출력을 중계하는 C++ 프로세스다. 연결은 공통 바이트 스트림(`TcpByteStream`) 위에 길이 프리픽스(`FramedConnection`)나 WebSocket(`WebSocketConnection`)을 얹은 것이다.

높음 2건이 핵심이다.
- 입장 도중 클라이언트가 끊기면 늦게 온 승인을 버려서, 그 캐릭터는 이 Gateway가 사는 동안 어디로도 다시 들어오지 못했다(G1).
- 메시지 처리 중에 연결을 끊으면 읽기 루프가 이미 해제된 연결을 읽었다(G2). Zone이 다른 Zone 번호로 응답하는 설정 실수 하나로 일어난다.

완료 조건: 지적마다 코드로 확인하고 고치며, 고친 경우는 수정 전 코드에서 실패하는 테스트로 고정한다. 소켓이 필요한 부분은 루프백 소켓으로 시험하고, 메모리 결함은 ASan에서 드러나게 한다.

## 고민한 선택지와 결정
| 주제 | 선택지 | 결정 |
|---|---|---|
| 처리 중 닫기(G2) | 각 연결의 읽기 함수에서 자기 참조를 잡음 / 닫힘 통지를 다음 루프로 미룸 / 호출할 콜백을 복사해서 부름 | 복사. 콜백 객체와 그것이 잡은 연결이 호출이 끝날 때까지 산다. 바이트 스트림과 두 연결에 같은 방식 하나를 쓴다. 통지를 미루면 닫힘 순서가 바뀌어 위쪽 코드가 영향을 받는다 |
| 입장 중 이탈(G1) | 닫힐 때 무조건 세션 종료 / Backend 답이 오면 판단 | 답을 보고 판단. 승인이면 세션 종료, 거절이면 할 일 없음, RPC 실패로 모르면 세션 종료. Backend가 이미 커밋했을 수 있고, 없는 세션을 끝내는 것은 아무 일도 하지 않는다 |
| 닫기 방식 | 보내고 바로 shutdown·close / 송신만 끊고 상대가 닫을 때까지 읽어 버림 | 후자. 읽지 않은 데이터가 남은 소켓을 닫으면 커널이 리셋을 보내 마지막 메시지(킥)가 사라질 수 있다 |
| 닫기 상한 | 모든 연결 / 신뢰할 수 없는 상대와 종료를 끝내야 하는 연결 | 클라이언트 연결(`protocol.close_linger_ms`)과 Gateway의 Zone 링크(`zone_link.close_linger_ms`). Zone 쪽 링크와 봇은 상대가 곧바로 닫으므로 상한 없이 둔다(호출 위치에 `std::nullopt`와 이유를 적었다) |
| Hello 시간 제한(G4) | 전송 계층 / 세션 | 세션. 시간은 세션이 재고, "아직 Hello 전인가"는 I/O 없는 상태 기계가 판단한다. 연결을 받은 순간부터 재서 WebSocket 핸드셰이크도 포함한다 |
| lease 상실(G5) | Gateway가 모든 세션을 내보냄 / Backend가 끝난 lease의 갱신을 거절 / 둘 다 | Gateway만. Gateway가 보는 lease는 Backend보다 안전 여유만큼 먼저 끝나서, Backend가 세션을 정리하기 전에 내보내기가 일어난다. 되살아난 lease에는 세션이 없다. Backend가 거절하면 Gateway에 새 인스턴스 ID로 다시 등록하는 경로가 필요한데, 그만큼 얻는 것이 없다. 26에서 미뤄 둔 Backend 쪽 거절은 그래서 넣지 않았다 |
| 종료(G6) | 유예 뒤 이벤트 루프 강제 정지 / 진행 중인 RPC를 세어 기다림 / RPC를 루프의 작업으로 잡고 자연히 끝냄 | 작업으로 잡음. `CallUnary`가 결과를 넘길 때까지 work guard를 쥔다. 연결 닫기와 RPC 모두 상한이 있으니 끝은 정해져 있다 |
| 세션 테스트의 경계 | `DirectoryClient`를 인터페이스로 / 실제 객체를 아무도 듣지 않는 주소로 | 후자. 세션 테스트는 RPC까지 가지 않고, 입장 로직은 상태 기계 테스트가 다룬다. 구현이 하나인 인터페이스를 만들지 않는다 |

## 리뷰에서 고친 것
| 지적 | 고친 것 |
|---|---|
| 입장 중에 클라이언트가 끊기면 늦게 온 승인을 버려 Backend 세션이 남는다(G1) | 상태 기계가 입장 중임을 기억해, 닫힌 뒤 온 승인은 세션 종료로 끝낸다. 결과를 모르는 RPC 실패도 세션 종료를 보낸다. 세션은 닫힌 뒤에도 Backend 답을 상태 기계에 넘긴다. 이 버그를 정상 동작으로 고정하던 테스트를 바꿨다 |
| 수신 콜백 안에서 연결을 끊으면 해제된 연결을 읽는다(G2) | 바이트 스트림과 두 연결이 콜백을 복사해서 부른다 |
| Hello·핸드셰이크에 시간 제한이 없고, 닫기가 flush를 끝없이 기다린다(G4) | `protocol.hello_timeout_ms`, 송신만 끊고 기다리는 닫기, 닫기 상한 |
| Gateway가 자기 lease 상실을 처리하지 않는다(G5) | lease를 잃으면 모든 세션을 `SERVICE_UNAVAILABLE`로 내보내고 Zone에서 떼어 낸다 |
| 종료 유예와 RPC 마감이 같고, 끝난 RPC가 사라진 이벤트 루프로 결과를 넘길 수 있다(G6) | 유예가 RPC 마감보다 길어야 시작한다. RPC는 결과를 넘길 때까지 루프의 작업이고, 루프를 강제로 멈추지 않는다. Zone 링크의 Stop이 진행 중인 이름 풀이와 접속을 취소한다 |
| 전송 계층·Zone 링크·세션·Listener 테스트가 없고, WebSocket이 조각난 제어 프레임을 받는다(G8) | 새 테스트 20개(전송 계층 8, Zone 링크 2, 세션·Listener 3, 설정 2, 상태 기계 5. 기존 2개는 이것들로 대체), 조각난 제어 프레임 거절(RFC 6455 §5.5) |
| "Token bucket"(실제는 고정 창), 맞지 않는 테스트 주석, 낡은 설명(G9) | 고정 창으로 설명, 테스트를 실제 개수대로, 전송 설명과 없는 설계 문서 참조 수정 |

미룬 것: 클라이언트 송신 큐 상한(G3)은 먼저 만든 이력대로 송신 역압·밀집 처리량 피처의 느린 클라이언트 kick에서 한다. 이번 닫기 상한으로 읽지 않는 클라이언트가 자리를 영영 잡지는 못한다. 규칙 위반(G7: `bool` 반환, 원시 정수 시간, 흩어진 상수, 설정 타입 오류 무시)은 규칙 정리 PR에서 한다. 이번에 새로 넣은 시간 값은 모두 `std::chrono`다.

  - 빌드: `main`을 뺀 전부를 `sa_gateway_core`로 묶었다
  - `SessionProtocol`: `redeem_in_flight_`, `OnHelloDeadline`, `OnServerClose`(킥 사유, `DETACH_REASON_GATEWAY_SHUTDOWN`)

## 만난 문제
- 처음 쓴 루프백 테스트가 멈췄다. 루프백에서는 쓰기가 시작하는 순간 상대에게 도착한다. 그래서 "상대가 데이터를 받았다"는 대기 조건이 이벤트 루프가 돌기 전에 이미 참이 됐다. 그 결과 송신 종료를 보내는 완료 핸들러가 실행되지 않았고, 상대의 블로킹 읽기가 끝나지 않았다. 상대 쪽 읽기를 논블로킹으로 바꾸고 기다리는 동안 이벤트 루프를 돌리게 했다.
- "읽지 않은 수신 데이터 때문에 닫기가 리셋이 되지 않는다" 테스트는 수정 전 코드에서도 통과했다. 루프백에서는 데이터가 즉시 전달되고, 대기 중인 읽기가 핸들러가 일찍 돌아가도 커널 버퍼를 비워서 리셋 상황이 재현되지 않는다. 증명하는 것이 없어 지웠다. 리셋으로 마지막 메시지가 사라지는 것은 지연이 있는 실제 네트워크에서 일어나는 일이다. 이 PR이 시험하는 것은 "송신만 끊고 상대가 닫을 때까지 기다린다"까지다.
- 테스트가 ASan의 누수 검사에 걸렸다. 연결과 그 바이트 스트림은 스트림이 끝날 때까지 서로를 잡는다. 실제 실행에서는 연결이 반드시 끝나서 풀리지만, 테스트가 연결을 연 채 끝나면 그대로 남는다. 테스트가 끝에서 연결을 끝내고, 가짜 연결도 실제 전송처럼 닫힘을 이벤트 루프로 알리게 했다.
- G2 재현 확인: 수정을 되돌린 상태에서 연결 재진입 테스트와 Zone 링크의 "다른 Zone의 환영" 테스트가 ASan에서 heap-use-after-free로 실패했다. 리뷰가 짚은 `FramedConnection::OnBytes`의 그 줄이다.

## 검증
- C++: dev 195 → 213개 통과, clang-tidy 경고 0, ASan·UBSan 213개 통과(누수 없음), 형식 검사 통과. 커밋 7개가 각각 빌드되고 테스트를 통과한다.
- 수정 전 코드에서 실패하는 새 테스트: 닫힌 뒤 온 승인의 세션 종료, 결과 모르는 입장의 세션 종료, 닫기가 상대를 기다림, 처리 중 닫기 재진입 둘과 다른 Zone 환영(ASan). 나머지는 새 함수·설정을 쓰므로 수정 전 코드로는 빌드되지 않는다.
- end-to-end 연속 실행. 기본: 봇 5개 전원 입장, 모순 0. 곧바로 전투: 처치 9, DB 처치 영수증 9, 모순 0. 두 실행 모두 Gateway는 SIGTERM 3.0초 뒤 스스로 끝났다(유예 3초).
- 세션이 살아 있는 종료: 개발 스택에서 전투 봇 6개가 플레이하는 중에 Gateway에 SIGTERM을 보냈다. 3.05초 뒤 끝났고, Backend의 열린 세션이 6에서 0이 됐다.
- 웹 뷰어(WebSocket): 헤드리스 브라우저가 입장해 늑대를 잡았다(모순 0, JS 오류 0). 브라우저를 닫은 뒤 Backend의 열린 세션은 0이다.

## 남긴 것
- Zone도 종료할 때 이벤트 루프를 강제로 멈춘다. 진행 중인 경제 RPC가 사라진 루프로 결과를 넘길 수 있는 같은 경쟁이 남아 있다. Zone의 Gateway 링크에는 닫기 상한이 없어 같은 방식의 자연 종료를 쓰려면 그것도 필요하다. 규칙 정리 PR에서 함께 본다.
- 클라이언트 송신 큐 상한(G3)은 송신 역압 피처, G7은 규칙 정리 PR.

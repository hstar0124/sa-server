# 36 (6단계) EventWorker 소비자: 확정 이벤트를 한 번씩 캐릭터 통계로

## 배경과 목표
영구 자산의 기준은 Backend(.NET)의 PostgreSQL 트랜잭션이다. 34에서 처치와 획득이 같은 트랜잭션에 Outbox 행을 남기게 됐고, 35에서 EventWorker가 그 행을 캐릭터마다 순번 순서로 Kafka(`game.character-events.v1`)에 발행하게 됐다. 발행은 적어도 한 번이라, 발행자가 Kafka의 확인 뒤에 죽으면 같은 이벤트가 다시 나간다. 이 PR은 그 이벤트를 읽어 조회 모델(`character_projections`, 33에서 만든 테이블)을 만드는 소비자다. 같은 이벤트가 몇 번 오든 효과는 한 번이어야 한다. Backend는 그 조회 모델로 캐릭터 통계를 보여 준다.

완료 조건:
- 같은 이벤트를 두 번 받아도 통계는 한 번만 움직인다.
- 적용할 수 없는 메시지가 파티션을 막지 않는다.
- 로컬 end-to-end가 이번 실행의 이벤트가 모두 한 번씩 적용됐는지 확인한다.

## 고민한 선택지와 결정
| 주제 | 선택지 | 결정 |
|---|---|---|
| 한 번만 적용하는 근거 | Kafka 오프셋 / Inbox 행과 같은 트랜잭션 | Inbox(`inbox_events`). 삽입과 통계 갱신을 한 트랜잭션에 넣고, 커밋한 뒤 오프셋을 커밋한다. 그 사이에 죽어 메시지가 다시 와도 기본 키 충돌로 아무것도 바뀌지 않는다 |
| 소비자 이름 | 고정 / 설정(Kafka 그룹 = Inbox 이름) | 설정. 이름을 바꿔 띄우면 토픽을 처음부터 다시 읽어 조회 모델을 다시 만들 수 있다. Inbox의 형식 CHECK와 같은 규칙을 설정 검증에도 건다 |
| 적용할 수 없는 메시지 | 모두 다시 읽기 / 영구 실패와 일시 실패를 나누기 | 나눈다. 디코딩 실패와 DB 제약 위반(SQLSTATE 23: 없는 캐릭터, 음수 등)은 실패 토픽으로 보내고 넘어간다. DB·브로커에 닿지 않는 경우만 같은 위치로 되돌아가 잠시 뒤 다시 읽는다 |
| 결과 표현 | 거절은 `null` / 결과 열거형에 `Rejected` | 열거형(`ApplyOutcome`: Applied, Duplicate, Ignored, Rejected). `null`이 결과 하나를 숨기지 않는다 |
| 통계 조회 | 소유 확인 뒤 따로 조회 / 한 문장 | 한 문장(캐릭터에 조회 모델을 LEFT JOIN). 소유가 아니면 행이 없어 404, 이벤트가 아직 없으면 0이다. 왕복이 하나이고, 확인과 조회 사이에 상태가 바뀔 틈이 없다 |
| end-to-end 판정 | 전체 합계 비교 / 이번 실행의 이벤트만 | 이번 실행의 Outbox 행이 소비자의 Inbox에 하나씩 있는지 본다. 개발 DB에는 이전 실행이 남긴 행이 있어, 전체 합계는 다른 실행의 상태에 흔들린다 |

## 구현
- `server/dotnet/EventWorker/Consuming/`
  - `CharacterStatsProjection`: 이벤트 → 증분, 순수 함수
  - `ProjectionStore`: Inbox 확보와 upsert, 한 트랜잭션
  - `CharacterStatsConsumer`: 소비 루프, 커밋 순서, 실패 토픽, 다시 읽기
  - `ConsumerOptions`: 그룹, 폴링·재시도 간격
- `Topics/KafkaOptions`: 실패 토픽(`game.failed-events.v1`, 파티션 1). 시작할 때 함께 만든다
- `appsettings.json`: `CharacterStatsConsumer` 절, 실패 토픽. 연결 풀 최소 3(발행자 락, 발행자 조회, 소비자)
- Backend `Modules/Characters`: `CharacterStats`, `CharacterRepository.ReadStatsAsync`, `GET /api/v1/worlds/{worldId}/characters/{characterId}/stats`
- 테스트
  - EventWorker 6개 추가(12개)
    - 같은 이벤트 두 번은 한 번 반영, 소비자 이름마다 따로, 모르는 종류는 기록만, 깨진 payload는 아무것도 쓰지 않음
    - Outbox → Kafka → 조회 모델 전체 경로에서 두 번 발행된 이벤트가 중복으로 걸러짐
    - 디코딩 실패는 실패 토픽으로 가고 뒤 메시지는 처리됨
    - 없는 캐릭터의 이벤트는 실패 토픽으로 가고 Inbox에도 남지 않음
  - Backend 통합 1개: 통계는 조회 모델에서 오고, 없으면 0이며, 다른 계정·다른 월드에는 404
- `scripts/e2e-local.sh`: 이번 실행의 이벤트가 발행되고 통계 소비자의 Inbox에 하나씩 들어갈 때까지 기다린다
- 설계 노트 08 확정 이벤트. README: EventWorker 행, 전체 구조, 데이터의 기준, 소비 규칙, 검증, Characters 모듈. 설계 노트 07의 "아직 안 한 것". `tests/integration/README.md`의 위치 안내

## 옮기면서 고친 것
- 이전 소비자는 DB 쓰기 실패를 모두 "잠시 뒤 다시"로 다뤘다. 없는 캐릭터를 가리키는 이벤트처럼 제약이 거절하는 행은 몇 번을 다시 해도 실패해서, 그 파티션이 영원히 멈췄다. 제약 위반은 실패 토픽으로 보낸다. 새 테스트는 이전 코드에서 예외로 실패한다.
- 이전 소비자는 거절을 `null`로 돌려줬다. 결과 열거형에 `Rejected`를 더했다.
- 이전 통계 조회는 소유 확인과 조회를 두 문장으로 했다. 한 문장으로 합쳤고, 다른 월드로 묻는 경우도 테스트에 더했다.
- 이전 end-to-end는 개발 DB 전체의 합계를 비교했다. 이번 실행의 이벤트만 본다.
- 이전 설계 노트 08은 순서 보장을 "커밋 순서 = 순번 순서라 시각 순 정렬이 뒤집히지 않는다"로 설명했다. 35에서 확인한 대로 틀린 설명이라, 실제 정렬 방법과 테스트로 다시 썼다. 발행자 락, 소비 실패의 두 갈래도 노트에 더했다. K3s 배포 부분은 37에서 다룬다.

## 만난 문제
- 없음. 로컬 Kafka는 이전 저장소와 같은 컨테이너를 쓰지만, 토픽에 남아 있던 메시지는 오늘 이 저장소가 발행한 32개뿐이었고 이전 소비자 그룹도 남아 있지 않았다. 새 소비자가 그 32개를 처음부터 적용했다.

## 검증
- .NET: 빌드 경고 0, `dotnet format` 통과. 단위 10개, Backend 통합 51개, EventWorker 12개 통과.
- C++: 변경 없음.
- end-to-end 획득(looters): PASS. 이번 실행의 이벤트 22개가 모두 발행되고 한 번씩 적용됐다. 소비자는 토픽에 남아 있던 이전 이벤트까지 54개를 적용했고, 중복·거절은 0이었다. 개발 DB 전체에서 처치 이벤트 28 = 조회 모델의 처치 합계 28, 획득 이벤트 26 = 획득 합계 26.

## 남긴 것
- K3s 배포(PostgreSQL·Kafka·Backend·EventWorker·Zone·Gateway 이미지와 매니페스트)는 37에서. 그것으로 6단계가 끝난다.
- Inbox와 발행된 Outbox 행의 보존 기간은 아직 없다.
- 소비자 그룹이 여러 인스턴스로 나뉠 때(재조정 중 오프셋 커밋 실패)는 Inbox가 중복을 거르지만, 실패한 커밋 뒤의 되돌리기가 이미 넘겨진 파티션에서 예외를 낼 수 있다. 지금은 인스턴스 하나다.

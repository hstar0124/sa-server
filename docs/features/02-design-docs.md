# 02 (0단계) 설계 문서, 첫 ADR 여덟 개, 설계 노트 다섯 개

## 배경과 목표
코드를 쓰기 전에 무엇을 만들고 왜 그렇게 만드는지를 글로 고정한다. 설계 문서는 기준점이고, 결정은 ADR로, 결정의 이유와 비교·수치 추정은 설계 노트로 남긴다. 이후 모든 피처는 이 문서들을 가리키며 시작한다. 완료 조건: 설계 문서 v1.0, ADR-0001~0008, 설계 노트 01~05, 작업 규칙(CLAUDE.md)과 README가 들어가고 서로 링크된다.

## 고민한 선택지와 결정
| 주제 | 선택지 | 결정 | 기록 |
|---|---|---|---|
| 설계 기준 | 문서를 계속 고치며 간다 / v1.0을 채택하고 변경은 ADR로 | 후자. 문서와 ADR이 충돌하면 ADR 우선 | ADR-0001 |
| 개발 순서와 환경 | 1단계부터 K3s / compose로 시작해 6단계에 K3s | 후자. 상태 있는 서비스가 셋이 되는 시점에 도입. 디스크는 재설치하지 않음 | ADR-0002 |
| 실시간 서버 언어 | C++23 / Rust / C# | C++23(GCC 14), 툴체인 고정 | ADR-0003 |
| 프로토콜 | Protobuf 단일 계약, 내부 gRPC, 게임 링크는 길이 프리픽스 TCP(UDP는 측정 뒤) | 채택 | ADR-0004, 설계 노트 01·02 |
| 입장 | 세션 토큰 조회 / 서명 티켓 + Backend 1회 소비 | 후자 | ADR-0005, 설계 노트 04 |
| 첫 클라이언트 | 게임 클라이언트 / 시드 기반 봇 | 봇. 부하 생성기이자 검증기 | ADR-0006 |
| Backend 데이터 접근 | EF Core / Npgsql+Dapper + SQL 마이그레이션, 모듈형 모놀리스 | 후자 | ADR-0007 |
| 시뮬레이션 코어 | 소켓·시계·난수를 직접 쓰는 서버 / 전부 주입받는 순수 라이브러리 | 후자 | ADR-0008, 설계 노트 05 |

설계 노트 03(밀집 전투)은 "AOI만으로 밀집을 풀 수 없다"는 추정을 수치로 남겨 두었다. 뒤 단계의 측정이 이 추정을 확인하거나 뒤집는다.

## 구현
- `docs/Server_Architecture.md`(v1.0), `docs/adr/0001`~`0008` + 색인, `docs/design-notes/01`~`05` + 색인
- `CLAUDE.md`: 코드 규칙 10개(숫자 리터럴 금지, 강타입 ID, 기능 단위 응집, 과분할 금지, 도메인은 I/O를 모름, 오류는 타입으로, DB 제약, 경고는 에러, 네이밍, 커밋), 작업 방식, 단계 표
- `README.md`: 구성 표, 문서 링크, 진행 상태, 빌드, 저장소 구성(계획). **이 시점에 존재하는 것만 적는다.** 증명 목록은 증명한 뒤에 생긴다.
- 자리만 잡은 README: `database/`, `deploy/k3s/`, `observability/`, `tests/integration/`

## 남긴 것
- 설계 문서 20절의 1단계 K3s는 ADR-0002로 6단계로 미뤘다. 17.2절의 파티션 계획도 실제 장비와 달라 따르지 않는다.
- 설계 문서의 "제안값"(틱 20 Hz, 스냅샷 10 Hz, AOI 40/45 m 등)은 측정 전까지 설정 기본값일 뿐이다.

# 24 23의 리뷰 수정: 획득과 처치 정산 보강

## 배경과 목표
23(Zone 드롭과 획득)을 병합한 뒤, 이미 옮긴 코드 전체를 회고 리뷰했다([2026-10-20 회고 리뷰](../reviews/2026-10-20-retrospective.md)). 이 저장소는 먼저 만든 이력을 피처 단위로 다시 쌓는데, 그동안은 "잘 옮겨졌는가"를 확인했을 뿐 "잘 짜였는가"는 피처마다 리뷰하지 않았다. 23의 변경분에서 중간 3건, 낮음 4건, 규칙 위반과 주석 몇 건이 나왔다. 대부분 Backend의 답이 없거나 늦거나 거절일 때의 처리다. 이 PR은 그것을 고친다. 완료 조건: 리뷰 지적마다 코드로 확인하고 고치며, 각 경우를 테스트로 고정한다.

## 고민한 선택지와 결정
| 주제 | 선택지 | 결정 |
|---|---|---|
| 답을 모를 때 | 클라이언트 재시도에 맡김 / Zone이 같은 요청을 다시 보냄 / 재조정 | 둘 다. 경제 호출 셋은 다시 보내도 안전하다(처치 ID, 요청 키, 읽기). 그래서 전송 실패는 같은 요청으로 정해진 횟수까지 다시 보낸다. 그래도 모르면 자산을 다시 읽어 Backend가 이미 넣은 아이템을 바닥에서 치운다 |
| 소유자가 아니라는 답 | 재시도하라는 "모름" / 최종 거절 + 세션 종료 | 최종 거절과 세션 종료. 이 Zone에서는 무엇도 확정될 수 없다. 클라이언트가 다시 입장하면 소유권이 새로 정해진다 |
| 처리 중인 요청의 재시도 | 기록(링)에서 찾기 / 예약에서 찾기 | 예약에서. 기록은 크기가 정해져 있어 다른 요청이 많으면 밀려난다. 예약은 답이 올 때까지 사라지지 않는다 |
| 재시도 기록의 크기 | 시뮬레이션 상수 / 계약 상수 | 계약(`COMMAND_RETRY_WINDOW`). 클라이언트와의 약속이다. 시뮬레이션은 Protobuf를 모르니 호스트가 설정(`ZoneConfig`)으로 넘긴다 |
| 처치 ID | 매번 OS 난수 / 인스턴스 ID와 순번에서 파생 | 파생(HMAC). 프로세스마다 인스턴스 ID가 달라 겹치지 않고, 틱 안에 예외 경로가 없다 |
| 골드의 순서 | 지갑 버전을 계약에 추가 / 큰 값 | 큰 값. 이 단계에서 골드는 오르기만 한다. 쓰는 기능(거래)이 들어올 때 지갑 버전을 더한다 |

## 리뷰에서 고친 것
| 지적 | 고친 것 |
|---|---|
| 답을 모르는 획득의 재시도가 Backend까지 가지 않아, Backend는 아이템을 넣었는데 바닥에 남고 인벤토리에 안 보일 수 있다 | 경제 호출 셋을 모두 같은 요청으로 재시도(`economy_call_attempts`)하고, 그래도 모르면 그 캐릭터의 자산을 다시 읽어 바닥 아이템과 인벤토리를 맞춘다 |
| "소유자 아님"·"같은 키 다른 본문"이 재시도하라는 "모름"으로 간다 | 최종 거절(`REJECT_CODE_NOT_OWNER`, `REJECT_CODE_INVALID_REQUEST`)로 바꾸고, 소유자가 아니면 세션을 내보낸다(`EVICT_REASON_NOT_OWNER`) |
| 입장 때 자산 조회가 한 번 실패하면 세션 내내 인벤토리 갱신이 없다 | 조회도 재시도하고, 다음 경제 응답이 오면 다시 묻는다 |
| 순서가 뒤바뀐 응답이 인벤토리 버전·골드를 되돌린다 | 버전은 큰 값만. 골드는 이 단계에서 오르기만 해서 큰 값을 받고, 쓰는 기능이 들어오면 지갑 버전을 계약에 더한다 |
| 처리 중인 획득이 다른 요청에 밀려 재시도 기록에서 빠지면 답이 두 번 나간다 | 처리 중인 획득은 예약으로 답하고, 재시도 기록에는 확정 결과만 둔다. 기록 크기는 계약 상수(`COMMAND_RETRY_WINDOW`)를 호스트가 넘긴다 |
| 요청 ID 0을 받아들인다 | 거절하고 기록하지 않는다 |
| 정산이 아이템 기준이라, 아이템이 사라진 뒤의 답은 요청자에게 닿지 않는다 | 예약 단위로 정산한다 |
| 처치마다 OS 난수를 쓰고 실패하면 예외가 틱 밖으로 나간다 | 처치 ID를 Zone 인스턴스 ID와 순번에서 HMAC으로 파생한다. 요청 키는 전용 16바이트 ID 타입 |
| "이미 가져감"을 "예약됨"으로 알린다, 스레드 설명 주석이 틀리다 | `ITEM_NOT_FOUND`로 알리고 주석을 고쳤다 |
| 드롭 산개 반경이 코드 상수, 597줄 테스트 파일 | `economy.toml [drops] scatter_radius_m`으로 옮기고, 호스트 테스트를 세션·경제 두 파일과 공용 픽스처로 나눴다 |

Economy 클라이언트의 재시도 정책 자체를 시험하는 테스트는 gRPC를 가짜로 바꿀 시험 경계가 필요해 규칙 정리 PR로 미뤘다.

## 구현
- 계약: `REJECT_CODE_INVALID_REQUEST`, `REJECT_CODE_NOT_OWNER`, `EVICT_REASON_NOT_OWNER`, `COMMAND_RETRY_WINDOW`
- `common`: `OpaqueId::FromExact`, `RequestKey`, `protocol::kCommandRetryWindow`
- `zone/sim`: 예약 단위 정산(`ResolvePickup(reservation, ...)`), Backend가 가진 바닥 아이템 정리(`RemoveSettledGroundItems`), 요청 ID 0 거절, 재시도 기록 크기를 설정에서, 산개 반경을 규칙에서
- `zone/server`: Economy 호출 공통 재시도, 소유자 아님 세션 종료, 자산 재조회, 버전·골드 순서, 처치 ID 파생, 설정 이름 `backend.economy_call_attempts`
- game-data: `economy.toml [drops] scatter_radius_m`
- 테스트: 호스트 테스트를 세션·경제 두 파일과 공용 픽스처로 나눔, 새 테스트 13개
- README: 요청 ID 거절과 재시도 범위, 답이 없을 때와 소유자가 아닐 때, ID 파생. 회고 리뷰 문서 링크
- 회고 리뷰 문서: 다섯 영역의 지적과 처리 계획

## 만난 문제
- 23 PR은 리뷰 결과가 나오기 전에 병합됐다. 리뷰 수정 커밋을 develop 위로 옮겨 이 후속 PR로 냈다.
- clang-tidy가 산개 반경 검증 `!(r >= 0 && r < range)`를 드모르간으로 단순화하라고 했다. 그대로 바꾸면 NaN이 통과한다. 그래서 NaN 검사를 명시하는 형태로 썼다.

## 검증
- C++: dev 169개 통과(23보다 13개 늘었다), clang-tidy 경고 0, ASan·UBSan 169개 통과, 형식 검사 통과.
- .NET: 코드 변경 없음(계약 생성 코드만 다시 만들어진다). 빌드 경고 0, 단위 4개·통합 33개 통과, `dotnet format` 통과.
- end-to-end(실행 사이에 lease 만료를 기다림, 013은 아직 열림): 기본은 봇 5개 전원 입장·모순 0. 전투는 시전 45, 처치 10, DB의 새 처치 영수증 10, 거절 0.

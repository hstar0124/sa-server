# 52 (8c) 느린 클라이언트 끊기, 그리고 옮기지 않은 두 가지

## 배경과 목표
8c(밀집 처리량)의 첫 PR이다. 이 프로젝트의 Gateway(C++)는 Zone이 보낸 스냅샷을 클라이언트마다 나눠 보낸다. 8b에서 Zone→Gateway 링크에는 예산을 둬 큐가 자라지 않게 했다(ADR-0011). 하지만 Gateway의 **클라이언트별 송신 큐**에는 상한이 없었다. 읽지 않는 클라이언트 하나가 Gateway 메모리를 끝없이 키울 수 있다. 8b를 마치고 머지된 코드를 점검하다 찾은 어긋남이다.

이전 이력의 8c 첫 커밋들은 이것과 함께 두 가지를 더 넣었다. 둘 다 이 장비에서 재 보니 나빠져서 옮기지 않았다(아래).
- Gateway↔Zone 링크의 명시적 소켓 버퍼(4 MiB)
- 읽기 단위 확대(16 KiB → 64 KiB)

완료 조건:
- 출력을 가져가지 않는 클라이언트는 정해진 양을 넘으면 끊기고 세션이 정리된다.
- 정상 부하(1,000명)에서는 한 명도 그 이유로 끊기지 않는다.

## 고민한 선택지와 결정
| 주제 | 선택지 | 결정 |
|---|---|---|
| 느린 클라이언트 | Gateway가 그 클라이언트의 스냅샷을 버림 / 끊기 | 끊기. Zone은 스냅샷마다 "알려준 집합"을 갱신한다. Gateway가 하나를 버리면 그 클라이언트는 생성·제거를 놓친 채 다음 변화만 받는다. 상태를 잃지 않고 버릴 수 있는 곳은 Zone(만들기 전, 51)뿐이다 |
| 킥 사유 번호 | 이전 이력의 `SLOW_CLIENT = 9` / 새 번호 | 10. 9는 48의 `IDLE_TIMEOUT`이다. Zone에 보내는 분리 사유도 `CLIENT_SLOW = 5`로 따로 둔다 |
| 판정 위치 | 세션 코드 / 순수 상태 기계 | 상태 기계(`OnZoneOutput`이 대기 바이트를 받는다). 48의 무응답 판정과 같은 방식이고 단위 테스트로 고정된다 |
| 링크 소켓 버퍼 명시 | 옮김 / 옮기지 않음 | 옮기지 않음(측정). 아래 |
| 읽기 단위 64 KiB | 옮김 / 옮기지 않음 | 옮기지 않음(측정). 아래 |

## 측정으로 옮기지 않은 것 (1,000명, release, 보고서 03과 같은 조건)
| | 51 (기준) | 소켓 버퍼 명시 + 읽기 64 KiB | 읽기 64 KiB만 | 이 PR |
|---|---|---|---|---|
| 미룬 스냅샷(구간) | 0 | 25,626~27,458 | 0 | 0 |
| Gateway 메모리 | 53 MiB | 98~99 MiB | 99~100 MiB | 53 MiB |
| Gateway CPU | 0.48 | 0.47~0.48 | 0.48~0.49 | 0.49 |
| Zone 놓친 틱 | 0 | 0 | 0 | 0 |

- **소켓 버퍼 명시.** 4 MiB를 요청했지만 커널은 `net.core.rmem_max`(이 장비 212,992바이트)로 잘랐다. 수신 버퍼를 명시하면 리눅스의 수신 창 자동 조정이 꺼진다. 자동 조정은 `tcp_rmem` 상한(6 MiB)까지 키울 수 있었는데, 명시하자 208 KB에 고정됐다. 링크가 덜 비워져 Zone의 예산이 발동했다(미룬 스냅샷 2만 5천여 개). 이전 이력이 이것을 넣은 이유는 봇 2,000명 진입 때의 루프백 교착이었다. 이 저장소에서는 아직 재현된 적이 없다. 8c 마무리(58)에서 2,000명을 잴 때 다시 보고, 재현되면 그 근거로 다룬다(예: 노드의 `rmem_max`를 올리고 확인).
- **읽기 단위 64 KiB.** 읽기 버퍼는 연결마다 객체 안에 들어 있다. 클라이언트 연결 1,000개면 연결당 48 KiB, 합해서 약 47 MB가 늘었다. CPU 이득은 보이지 않았다.

## 구현
- 계약: `KICK_REASON_SLOW_CLIENT = 10`, `DETACH_REASON_CLIENT_SLOW = 5`
- Gateway
  - `SessionProtocolConfig::max_send_queue_bytes`(`protocol.max_send_queue_bytes`, 1 MiB, 0은 거절)
  - `OnZoneOutput(from, message, queued_bytes)`: 넘으면 킥·분리·세션 종료
  - `ClientSession`이 연결의 `QueuedBytes()`(피처 50)를 넘긴다

## 지킨 것 (이번 저장소의 개선)
- 48의 생존 확인·무응답 기한과 킥·분리 사유 번호
- 50의 `QueuedBytes()`(이 판정의 입력)와 51의 링크 예산(링크 쪽 밀림은 Zone이, 클라이언트 쪽 밀림은 Gateway가 맡는다)

## 옮기면서 고친 것
- 킥 사유 번호 충돌(9)을 피했다. Zone 쪽 분리 사유를 따로 두어 로그에서 구분한다.
- 이전 이력의 소켓 버퍼 지정은 연결이 맺어진 뒤에 했다. tcp(7)에 따르면 `connect`/`listen` 전에 해야 창 배율에 반영된다. 연결 전으로 옮기는 구현까지 해 봤지만, 위 측정대로 명시 자체가 이 장비에서 손해라 넣지 않았다.

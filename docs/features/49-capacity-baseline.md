# 49 용량 기준선: 봇 50~1,000명, 측정 스크립트와 보고서 02

## 배경과 목표
이 프로젝트의 실시간 경로는 Gateway(클라이언트 연결)와 Zone(지도 하나의 20 Hz 시뮬레이션)이다. 8단계에서 Zone이 둘이 됐다. 다음 단계(송신 역압)는 처리량을 바꾸는 일이라, 바꾸기 전에 지금 상태를 같은 도구로 다시 잴 수 있게 재 둔다. 질문은 "스택 하나가 봇 몇 명까지 받고, 먼저 휘는 곳은 어디인가"다.

완료 조건:
- 스크립트 한 번으로 release 빌드 스택을 띄우고, 봇 N명을 돌리고, 측정 결과를 마크다운으로 낸다. 결과는 프로세스별 CPU·메모리, Zone의 틱 상태, 봇의 판정이다.
- 50·100·200·500·1,000명을 재서 보고서로 남긴다.

## 고민한 선택지와 결정
| 주제 | 선택지 | 결정 |
|---|---|---|
| 빌드 | dev / release | release(C++ `release` 프리셋, .NET `Release`). Debug 숫자는 용량 숫자가 아니다. `dev-stack.sh`가 `SA_BUILD`·`SA_DOTNET_CONFIG`를 받는다 |
| 봇 구성 | 한 역할 / 섞어서 | 섞어서(전투 60 %·획득 20 %·배회 20 %). 이동·전투·드롭을 함께 건드린다 |
| 측정 구간 | 실행 전체 / 준비 뒤부터 끝 전까지 | 봇 준비(가입은 비밀번호 해시라 느리다) 뒤 5초부터 끝 10초 전까지. 준비와 종료가 CPU에 섞이지 않는다 |
| 원인 가르기 | 숫자만 / 대조 실행을 함께 | 대조 실행을 함께 했다. 1,000명에서 휘자 세 가지를 따로 쟀다. 체크포인트를 끈 실행, 네트워크 없이 프로세스 안 봇 1,000개, 진입 중 링크 소켓 큐 관찰이다 |

## 구현
- `scripts/bench/capacity.sh <봇 수> [초]`
  - release 바이너리가 없으면 멈춘다.
  - 프로파일 틀에 봇 수를 넣고 스택을 띄운 뒤 측정 구간 동안 다음을 모은다.
    - 프로세스 여섯(Zone A·B, Gateway, Backend, EventWorker, loadgen)의 CPU(`/proc/<pid>/stat`)와 최대 RSS(`VmHWM`)
    - 컨테이너 셋의 `docker stats`
    - 두 Zone의 10초 통계 줄(틱, 놓친 틱, 지연)
    - 봇 보고서
  - 끝나면 스택을 내린다.
- `scripts/bench/capacity-profile.toml`: 봇 수와 실행 시간 자리를 둔 프로파일 틀
- `scripts/dev-stack.sh`: `SA_BUILD`(기본 `build/dev`), `SA_DOTNET_CONFIG`(기본 `Debug`)
- 보고서 02, 이슈 020(열림), README "성능과 개선"과 빌드 절, CLAUDE.md 단계 목록

## 옮기면서 고친 것
- 이전 이력의 스크립트는 Zone A의 틱 상태만 읽었다. 두 Zone을 모두 읽는다.
- 이전 이력은 스택 시작 실패를 버리고(`>/dev/null`) 다음 단계로 갔다. 실패하면 시작 로그를 보여 주고 멈춘다. 실행 시간이 측정 구간보다 짧으면 시작하지 않는다.
- 이전 이력에서 측정 중 고친 봇 티켓 만료(가입을 다 끝낸 뒤 접속해 앞쪽 봇의 티켓이 만료)는 이 저장소의 loadgen에 이미 반영돼 있다(준비 단계와 티켓 단계 분리). 1,000명 모두 입장했다.
- 이전 이력의 수치는 옮기지 않았다. 보고서 02의 모든 숫자는 이 저장소에서 2026-10-23에 잰 것이다.

## 만난 문제
- [이슈 020](../issues/020-overloaded-gateway-mistaken-for-a-dead-one.md)(열림): 1,000명 진입 폭주 중 Gateway의 이벤트 루프가 5초 넘게 밀렸다. Zone이 침묵으로 판정해 링크를 닫았고, 네 번 중 한 번 세션이 모두 끊겼다. 근본 원인은 Gateway 처리량이고 8b 송신 역압에서 다룬다.

## 검증
- 측정 결과(보고서 02)
  - 50~500명: 선형이고, 500명에서 Zone·Gateway 각 0.25코어, 틱 지연 50 µs 아래, 놓친 틱 0
  - 1,000명: 진입 직후 30초간 놓친 틱 57~59, Zone A 메모리 1.1~1.2 GiB(링크 송신 큐), Gateway 0.72코어. 그 뒤 놓친 틱 0
  - 네트워크 없이 1,000명은 놓친 틱 0이다. 체크포인트를 꺼도 같다
- 스크립트: 다섯 규모를 차례로 돌려 모두 끝까지 갔다. 1,000명 1회차는 이슈 020으로 FAIL이다. 끝나면 스택이 내려가 있다.
- C++·.NET 코드 변경 없음.

## 남긴 것
- 8b 송신 역압 뒤 같은 스크립트로 1,000명을 다시 잰다. 그때 이슈 020의 판정 근거(이벤트 루프 지연, 마지막 수신 뒤 최대 간격)도 남긴다.
- 두 Zone에 나눈 1,000명, 밀집 전투, 봇을 다른 장비에서 돌리는 측정은 보고서 02의 "다음에 잴 것"에 적었다.

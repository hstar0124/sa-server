# 17 CI 의존성 캐시: 버전을 올려도 의존성을 다시 빌드하지 않는다

## 배경과 목표
4단계가 끝나 0.2.0을 내려고 버전이 적힌 곳을 찾다가, 릴리스 커밋 하나가 CI 의존성 캐시를 무효로 만든다는 것을 발견했다([이슈 008](../issues/008-version-bump-invalidates-the-ci-dependency-cache.md)). 캐시 키가 `vcpkg.json` 전체의 해시인데, 그 파일에 제품 버전이 들어 있었다. 이대로면 릴리스 PR마다 gRPC·protobuf·abseil을 처음부터 빌드하고, 그건 2시간이 넘는다. 릴리스 브랜치에는 버전과 문서만 넣는 것이 원칙이라, CI 수정은 develop으로 가는 수정 PR로 먼저 낸다. 완료 조건: `vcpkg.json`이 바뀐 이 PR 자체에서 의존성 잡이 처음부터 빌드하지 않고 끝난다.

## 고민한 선택지와 결정
| 주제 | 선택지 | 결정 |
|---|---|---|
| 키가 어긋났을 때 | 처음부터 빌드 / 같은 트리플릿의 최근 캐시로 대체 | 대체(`restore-keys`). 캐시는 패키지별 ABI로 이름 붙은 아카이브라, vcpkg가 바뀌지 않은 패키지는 그대로 쓰고 바뀐 것만 빌드한다 |
| 키 계산 | `vcpkg.json` 전체 해시 유지 / `dependencies`·`builtin-baseline`만 해시 | 전체 해시 유지. 부분 해시는 키를 만드는 단계가 하나 늘고, 의존성을 하나 올리면 결국 처음부터 빌드한다. 대체 키가 그 경우도 덮는다 |
| 제품 버전 위치 | CMake와 vcpkg.json 두 곳 / CMake 한 곳 | CMake 한 곳. vcpkg는 최상위 매니페스트에 버전을 요구하지 않는다. 같은 값을 두 곳에 두지 않는다는 규칙에도 맞고, 릴리스 커밋이 의존성 매니페스트를 건드리지 않게 된다 |
| 어디로 내나 | 릴리스 브랜치에서 함께 / develop으로 가는 수정 PR | 수정 PR. 릴리스 브랜치에 CI 변경을 섞지 않는다 |

## 구현
- `.github/workflows/ci.yml`: 의존성 잡의 복원 단계에 `restore-keys`. C++ 세 잡은 그대로 정확한 키를 요구한다. 의존성 잡이 먼저 새 키로 저장하기 때문이다
- `vcpkg.json`: `version-string` 제거
- CONTRIBUTING.md: 릴리스에서 바꾸는 것은 루트 `CMakeLists.txt`의 버전과 피처 색인뿐
- 이슈 008

## 만난 문제
- [008](../issues/008-version-bump-invalidates-the-ci-dependency-cache.md) 릴리스 버전 한 줄이 CI 의존성 캐시를 무효로 만든다. 실제로 터지기 전에 릴리스 준비 중에 찾았다.
- 로컬에서 "버전을 빼도 의존성 ABI가 그대로인가"를 시험할 때, 처음에는 툴체인 밖에서 돌려 시스템 컴파일러를 잡았다. 그래서 전부 다시 빌드한다는 결과가 나왔다. gcc-toolset-14 안에서 원래 매니페스트와 바꾼 매니페스트를 나란히 돌려 비교했다.

## 검증
- 로컬: gcc-toolset-14 안에서 원래 매니페스트와 버전을 뺀 매니페스트로 `vcpkg install --dry-run`을 각각 돌렸고, 둘 다 "already installed"였다. `cmake --preset dev`의 vcpkg 설치 단계도 다시 빌드 없이 끝났고, C++ 140개가 통과했다.
- CI: 이 PR은 `vcpkg.json`이 바뀌어 정확한 캐시 키가 없다. 의존성 잡이 대체 키로 develop의 캐시를 복원하고 얼마 만에 끝났는지를 머지 전에 여기에 적는다.

## 남긴 것
- 대체 키로 복원한 캐시에는 쓰지 않는 옛 아카이브가 남아 새 키로 함께 저장된다. 의존성을 올릴 때마다 조금씩 커진다. 의존성을 미리 빌드한 CI 이미지로 옮기면 이 캐시 자체가 필요 없어진다.
- 이 PR 뒤에 0.2.0 릴리스 브랜치를 딴다. 그 릴리스 커밋은 CMake 버전과 피처 색인만 바꾼다.

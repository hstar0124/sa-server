# 40 (7단계) 킬 랭킹 기준선: PostgreSQL로 리더보드와 내 순위, 그리고 측정

## 배경과 목표
7단계는 랭킹이다. 캐릭터별 처치 수는 6단계에서 EventWorker가 확정 이벤트로 만드는 통계 조회 모델(`character_projections`)에 이미 있다. 작업 규칙상 새 구성 요소(여기서는 Redis)를 들이기 전에 기준선을 먼저 재야 한다. 이 PR은 PostgreSQL만으로 랭킹 API를 만들고, 같은 조건에서 다시 잴 수 있는 측정 도구와 스크립트를 함께 넣어 기준선을 잰다. Redis로 옮기고 다시 재는 것은 다음 PR(41)이다.

완료 조건: 리더보드와 내 순위가 동점 규칙까지 테스트로 고정되고, 10만·100만 캐릭터에서 잰 기준선이 보고서에 있다.

## 고민한 선택지와 결정
| 주제 | 선택지 | 결정 |
|---|---|---|
| 순위의 정의 | 동점은 같은 순위 / 동점은 캐릭터 ID로 | 캐릭터 ID가 낮은 쪽이 앞. 순위가 전순서(total order)라 페이지를 넘겨도 같은 캐릭터가 두 번 나오거나 빠지지 않는다 |
| 내 순위 계산 | 전체 정렬 뒤 위치 / 나보다 앞선 행 세기 | 앞선 행 세기. 인덱스 범위만 읽는다. 그래도 순위가 낮을수록 셀 행이 많다. 그 비용이 이번 측정의 대상이다 |
| 인덱스 | 없음 / `(world_id, kills DESC, character_id)` | 인덱스(마이그레이션 0007). 리더보드는 앞에서 N개만, 순위는 앞쪽 범위만 읽는다 |
| 페이지 크기 | 범위 밖이면 400 / 범위 안으로 맞춤 | 맞춤(1~`MaxTop`). 답은 여전히 리더보드다. 기본 페이지가 최대보다 크면 시작하지 않는다 |
| 측정 도구 | 외부 도구(wrk 등) / 저장소 안의 작은 도구 | 저장소 안(`tools/httpbench`). 보고서의 숫자를 같은 도구로 다시 낼 수 있다. 클라이언트 N개가 응답을 받자마자 다음 요청을 보내는 닫힌 루프, 지연 백분위 |

## 구현
- Backend `Modules/Rankings`
  - `GET /api/v1/worlds/{worldId}/rankings/kills?top=N`
  - `GET /api/v1/worlds/{worldId}/characters/{characterId}/rank`(기록이 없으면 404)
  - 설정 `Rankings:MaxTop`·`DefaultTop`(기본 100·20, DefaultTop ≤ MaxTop 검증)
- `database/migrations/0007_ranking_index.sql`
- `tools/httpbench`(솔루션의 tools 폴더)
- `scripts/bench/ranking.sh run <N> [clients] [sec] | clean`, `scripts/bench/seed-rankings.sql`
- 보고서 01(기준선), README의 Backend 표·구성도, 자산 절의 랭킹 항목, 새 "성능과 개선" 절, 저장소 구성
- 통합 테스트 3개
  - 처치 수 순서, 동점은 낮은 ID, 순위는 앞선 수 + 1
  - 기록 없는 캐릭터와 다른 월드는 404
  - 페이지 크기는 범위 안으로
  - 기본 페이지가 최대보다 크면 Backend가 시작하지 않음

## 옮기면서 고친 것
- 이전 엔드포인트는 경로 값을 원시 `long`으로 받아 안에서 ID로 바꿨다. 31에서 정한 대로 `WorldId`·`CharacterId`를 바로 받는다.
- 이전 설정은 기본 페이지가 최대보다 커도 받아들였다(조용히 잘렸다). 시작에서 거절한다.
- 이전 리더보드는 캐릭터 이름을 ID만으로 조인했다. 33에서 건 복합 키(월드, 캐릭터)로 조인한다.
- 이전 벤치 스크립트는 100만 개의 벤치 계정·캐릭터를 개발 DB에 남겼다. `clean`으로 지운다.
- 이전 httpbench는 숫자가 아닌 인자에 예외로 죽었다. 사용법을 출력한다. 준비 요청의 응답도 해제한다.
- 측정은 이전 이력의 숫자를 옮기지 않고 이 저장소에서 다시 쟀다.

## 만난 문제
- 순위 질의를 다시 쓰다 버그를 만들었다. 집계(`count`)는 `GROUP BY`가 없으면 입력이 없어도 한 행을 돌려준다. 그래서 기록 없는 캐릭터가 "1위, 처치 0"으로 나왔다. 새 테스트가 잡았고 `GROUP BY`로 고쳤다. 이전 이력의 질의는 교차 조인이라 이 문제가 없었다.

## 검증
- .NET: 빌드 경고 0, `dotnet format` 통과. 단위 10개, Backend 통합 51 → 54개, EventWorker 12개 통과.

- 측정 뒤 벤치 데이터를 지웠다(남은 통계 행 5개는 원래 있던 것).

# 35 (6단계) EventWorker 발행자: Outbox를 Kafka로, 캐릭터마다 순서대로, 발행자는 하나

## 배경과 목표
영구 자산의 기준은 Backend(.NET)의 PostgreSQL 트랜잭션이고, 34에서 처치 기록과 획득이 같은 트랜잭션에 Outbox 행(`outbox_events`)을 남기게 됐다. 행에는 캐릭터(집합)마다 1부터 빈틈없이 오르는 순번이 붙는다. 이 PR은 그 행을 Kafka로 내보내는 EventWorker(.NET 워커 프로세스)를 만든다. 다음 PR(36)의 소비자가 이 이벤트로 조회 모델을 만든다.

완료 조건:
- 한 캐릭터의 이벤트는 순번 순서로만 나간다. 한 이벤트가 실패하면 그 캐릭터만 멈추고 다른 캐릭터는 계속 나간다.
- 브로커가 확인한 이벤트만 발행됨으로 표시한다. 그 사이에 죽으면 다시 나간다(적어도 한 번).
- 인스턴스가 둘 떠도 발행자는 하나다.
- 로컬 end-to-end가 실행 중 쓰인 이벤트를 모두 발행했는지 확인한다.

## 고민한 선택지와 결정
| 주제 | 선택지 | 결정 |
|---|---|---|
| 브로커 | compose에 Kafka / PostgreSQL LISTEN·NOTIFY나 큐 테이블만 | Kafka(KRaft 단일 노드, 자동 토픽 생성 끔, 24시간·2 GiB 보관). 설계 기준이 Outbox → Kafka → Inbox이고, 이후 랭킹 소비자도 같은 토픽을 읽는다. 기준 기록은 Outbox와 원장이라 보관은 짧게 둔다 |
| 가져오는 순서 | 트랜잭션 시작 시각(`occurred_at`) 순 / 캐릭터별로 묶어 순번 순, 캐릭터는 가장 오래 기다린 것부터 | 후자. `occurred_at`은 트랜잭션이 시작한 시각이다. 먼저 시작한 트랜잭션이 순번 잠금은 나중에 잡을 수 있어서, 순번 2가 순번 1보다 이른 시각을 가질 수 있다. 시각 순으로 묶음을 자르면 2가 먼저 나간다. 캐릭터별로 묶으면 묶음 제한은 뒤쪽만 자른다 |
| 동시에 뜬 인스턴스 | 배포에서 하나만 띄우기로 약속 / DB 락으로 강제 | PostgreSQL advisory lock. 쥔 인스턴스만 발행하고 나머지는 대기한다. 롤링 배포는 잠깐 두 인스턴스를 겹치게 한다. 두 발행자가 각자 순서를 지켜도 서로 끼어들면 순서가 섞인다 |
| 락을 잃는 경우 | 무시 / 매 차례 확인 | 매 차례 확인. 세션 락은 연결이 끊기면(DB 재시작) 조용히 사라지고, 그사이 다른 인스턴스가 잡을 수 있다. 차례마다 `pg_locks`에서 자기 세션이 쥐고 있는지 본다 |
| 락 해제 | 연결을 닫으면 풀린다고 기대 / 명시적으로 풀기 | 명시적으로 푼다. Npgsql 풀은 닫힌 연결을 세션째 보관해서, 닫아도 락이 남는다. 테스트가 이것을 잡았다 |
| 라우팅할 토픽이 없는 행 | 매 차례 가져와 건너뛰고 오류 로그 / 가져오지 않고 시작할 때 한 번 알림 | 후자. 그런 행은 영원히 가장 오래된 행이라 매 묶음의 앞자리를 차지하고, 수가 묶음 크기를 넘으면 정상 행이 하나도 못 나간다. 오류 로그도 0.5초마다 쌓인다 |
| 전달 제한 시간 | 호출만 취소 / 프로듀서의 메시지 제한 시간도 같게 | 같게(`MessageTimeoutMs = PublishTimeout`). 발행자가 포기한 메시지를 librdkafka가 뒤에서 계속 재시도하지 않는다 |
| 토픽 | 캐릭터·월드·실패 셋을 미리 / 쓰는 것만 | 캐릭터 토픽 하나. 월드 이벤트는 아직 쓰는 곳이 없고, 실패 토픽은 소비자(36)와 함께 들어온다 |
| 로컬 실행 | 소비자와 함께(36) / 이 PR부터 | 이 PR부터. 스크립트가 EventWorker를 먼저 띄우고 마지막에 내리며, end-to-end가 "이번 실행의 이벤트가 모두 발행됐다"를 확인한다. 발행자만으로도 검증할 것이 있다 |

## 구현
- `deploy/compose/docker-compose.yml`: `kafka`(apache/kafka 3.9.0, KRaft 단일 노드, 127.0.0.1:9092, 메모리 1 GiB, 헬스체크)
- `server/dotnet/EventWorker`
  - `Infrastructure/DatabaseOptions`: 연결 문자열(환경 변수나 user-secrets로만), 풀 크기
  - `Topics/`: `KafkaOptions`(부트스트랩, 복제 계수, 캐릭터 토픽), `TopicRouting`(집합 종류 → 토픽, 키 `월드:집합`), `KafkaTopicProvisioner`(시작할 때 없는 토픽 생성, 있으면 그대로)
  - `Publishing/`
    - `OutboxRepository`: 묶음 가져오기, 발행 표시, 라우팅 없는 행 세기, 발행자 락(`PublisherLock`: 확인과 해제)
    - `OutboxPublisher`: 한 차례(`PublishPass`)
    - `IEventProducer`/`KafkaEventProducer`: 멱등 프로듀서, 모든 ISR의 확인, 헤더에 이벤트 종류
    - `OutboxPublisherService`: 락을 쥐고 차례를 반복한다. 묶음이 가득 찼으면 곧바로 다음 차례, 아니면 주기를 기다린다
  - `appsettings.json`: 연결 문자열은 빈 값
- 패키지: Confluent.Kafka 2.15.1, Testcontainers.Kafka 4.16.0
- `server/dotnet/tests/EventWorker.Tests`(실제 PostgreSQL과 Kafka, Testcontainers) 6개
  - 캐릭터별 순번 순서와 확인 뒤 표시
  - 실패한 이벤트는 그 캐릭터만 멈춘다
  - 묶음 크기 1에서도, 먼저 시작한 트랜잭션의 순번 2가 1보다 먼저 나가지 않는다
  - 토픽 없는 종류의 행은 보내지 않고 묶음을 막지도 않는다
  - 락은 한 인스턴스만, 풀면 다른 인스턴스가, 세션이 끊기면 쥔 쪽이 알아챈다
  - 실제 브로커: 키와 내용, 확인 뒤 죽으면 같은 이벤트 ID가 다시 나간다
- `scripts/e2e-local.sh`, `scripts/dev-stack.sh`: EventWorker를 먼저 띄우고 마지막에 내린다. end-to-end는 이번 실행이 쓴 Outbox 행이 모두 발행될 때까지 기다리고, 못 하면 실패다
- README: 전체 구조, 프로그램 표, 데이터의 기준, 자산 절의 발행 규칙, 검증, 기술 선택, 배포 그림, 저장소 구성

## 옮기면서 고친 것
- 이전 발행자는 `occurred_at` 순으로 묶음을 잘랐다. 주석은 "한 집합의 커밋 순서가 순번 순서라 뒤집히지 않는다"고 했지만, `occurred_at`은 커밋이 아니라 시작 시각이다. 순번이 뒤바뀐 두 행이 묶음 경계에 걸리면 뒤 순번이 먼저 나갈 수 있었다. 새 테스트는 이전 정렬에서 실패하고 지금 정렬에서 통과한다.
- 이전 발행자는 "인스턴스 하나만 발행한다"를 주석으로만 가정했다. advisory lock으로 강제하고, 락을 잃는 경우와 풀 때의 함정을 테스트로 고정했다.
- 이전 발행자는 라우팅할 수 없는 행을 매 차례 가져왔다. 그런 행이 쌓이면 발행이 멈출 수 있었고 오류 로그가 0.5초마다 찍혔다.
- 이전 `appsettings.json`에는 비밀번호가 든 연결 문자열이 있었다. 비밀 값은 설정 파일에 두지 않는다는 규칙대로 비웠다. 스크립트가 환경 변수로 준다.
- 쓰는 곳 없는 월드·실패 토픽과 `world` 라우팅을 뺐다. 프로듀서의 재시도 횟수 5와 종료 시 5초는 이름 붙은 값이나 발행 제한 시간으로 바꿨다.
- 주석의 설계 문서 절 번호는 지우고 이유를 그 자리에 적었다.

## 만난 문제
- 스크립트가 EventWorker를 저장소 루트에서 실행하자 `appsettings.json`을 못 찾아 시작 검증에서 멈췄다. 워커의 설정 루트는 작업 디렉터리다. Backend처럼 프로젝트 디렉터리에서 실행하게 했다.
- 락 테스트가 처음에 실패했다. 해제가 "연결 닫기"였는데, 풀이 세션을 살려 둬 락이 남았다. 명시적 해제를 더했다(위 결정).

## 검증
- .NET: 빌드 경고 0, `dotnet format` 통과. 단위 10개, Backend 통합 50개, EventWorker 6개 통과.
- 새 순서 테스트는 이전 정렬(`ORDER BY occurred_at, ...`)로 바꾸면 실패한다.
- C++: 변경 없음.
- end-to-end 획득(looters): PASS. 이번 실행이 쓴 이벤트 15개(처치 8, 획득 7)가 모두 발행됐다. 첫 차례는 이전 실행들이 남긴 미발행 행 17개도 함께 보냈다.
- 대화형 스택: `up`에서 EventWorker가 발행자로 서고, `down`에서 마지막에 정상 종료한다.

## 남긴 것
- 소비자(Inbox로 한 번씩 적용, 캐릭터 통계 조회 모델, 실패 토픽)는 36에서.
- 집합 종류 이름 `character`는 Backend(`EventAggregate.Character`)와 EventWorker(`TopicRouting.CharacterAggregate`)에 따로 있다. 두 .NET 프로세스가 함께 쓰는 공용 프로젝트가 생기면 한 곳으로 모은다.
- 발행된 Outbox 행의 정리(보존 기간)는 아직 없다.
- DB가 끊기면 발행자 서비스가 예외로 멈추고 프로세스가 끝난다. 다시 띄우는 것은 실행 환경(K3s, 37)의 몫으로 둔다.

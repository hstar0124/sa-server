# 59 (9단계) Backend 거래 모듈: 협상은 테이블에, 확정은 트랜잭션 하나에

## 배경과 목표
거래는 Backend(.NET)가 협상 상태를 소유한다(ADR-0013). 58에서 테이블과 계약을 놓았고, 이 PR은 `Trade` gRPC 서비스를 구현한다. 서비스는 열기, 제안, 동의, 취소 네 가지다. Zone은 이 서비스를 부르고 결과를 클라이언트에 중계한다(60).

완료 조건:
- 모든 호출이 PostgreSQL 트랜잭션 하나이고 요청 id로 멱등이다.
- 양쪽이 같은 버전에 동의한 순간 같은 트랜잭션에서 확정한다.
- 확정이 중간에 거절되면 아무것도 움직이지 않는다.
- 통합 테스트(실제 PostgreSQL)가 자산 보존, 단일 확정, 잠금, 거절, 이탈·만료를 덮는다.

## 고민한 선택지와 결정
| 주제 | 선택지 | 결정 |
|---|---|---|
| 소유권 확인과 요청 id 확보 | Economy 코드 복사 / 공용으로 옮기기 | 공용으로(`Common/ZoneAuthority.cs`의 `CharacterOwners`, `Common/CommandResults.cs`). Economy의 private 메서드였다. 동작은 그대로이고 기존 통합 테스트 65개가 통과한다 |
| 확인 순서 | 권한 먼저(이전 이력) / 저장된 결과 먼저 | 획득과 같은 순서. 이미 판정된 요청은 저장된 결과로 답하고, 그다음 소유권(낡은 소유자는 `STALE_AUTHORITY`, 저장하지 않음), 그다음 요청 id 확보 |
| 맞교환의 주차 칸 | 음수 칸(이전 이력) / 용량 이상의 칸 | 용량 이상. `max(용량, 가진 칸 최대 + 1) + k`. 용량이 줄어 그보다 높은 칸에 아이템이 있는 인벤토리도 덮는다. 빈 칸 계산(유효 칸 − 가진 칸 + 내보낸 칸)이 그대로 용량 검사다 |
| 확정 중 거절 | 그대로 커밋(이전 이력) / savepoint로 되돌림 | 되돌림. 이전 이력은 금화를 뺀 뒤 다음 단계가 거절하면 뺀 금화가 커밋되는 결함이 있었다. 이제 확정을 savepoint 안에서 하고, 거절이면 되돌린 뒤 양쪽 동의를 지우고 거래는 열어 둔다. 테스트가 되돌리기를 빼면 실패하는 것을 확인했다 |
| 금화 순서 | 한쪽씩 차감·가산 / 모두 차감한 뒤 가산 | 모두 차감 먼저. 받을 금화로 내 제안을 치르는 일이 없다 |
| 요청 해시 | 필드만 / 명령 종류부터 | 종류부터. 이전 이력은 같은 거래에서 "금화 G 제안"과 "버전 G 동의"의 해시가 같아, 같은 요청 id로 다른 명령을 보내도 거절되지 않았다 |
| 만료 | 그 거래를 만질 때만 / 열 때 두 캐릭터의 만료 거래도 닫기 | 후자. 취소를 놓친 거래(예: Zone이 죽음)가 그 캐릭터를 `ALREADY_TRADING`으로 계속 막지 않는다 |
| 원장 | 사유 `trade:<id>`, 통화 "gold" 고정(이전 이력) / 사유 `trade`, 통화는 콘텐츠의 기본 통화 | 후자. 58의 CHECK와 원장 모양 CHECK에 맞는다 |

## 구현
- `Modules/Trading/`
  - `Ids.cs`: `TradeId`
  - `Trade.cs`: 결과·상태, 명령 네 가지, 요청 해시
  - `TradingRepository.cs`: 모든 호출의 틀(저장된 결과, 소유권, 요청 id 확보, 실행, 저장)과 열기·제안·동의·취소, 만료
  - `TradeSettlement.cs`: 확정 트랜잭션. 인벤토리를 캐릭터 id 순으로 잠그고, 아이템 소유 재확인, 칸 계산, 금화, 두 번에 걸친 아이템 이동, 인벤토리 버전, 원장, 참여자마다 `TradeCompleted` Outbox
  - `TradeRecords.cs`: 거래 행 잠금, 아이템 목록, 상태 보기, 닫기(참여·아이템 행 삭제), 재전송용 저장 결과
  - `TradingGrpcService.cs`: proto ↔ 도메인 변환. 형식이 틀린 입력은 `InvalidArgument`
  - `TradingModule.cs`, `TradingOptions.cs`: `Trading:ExpirySeconds`(기본 60, 1~3600, 시작 시 검증)
- `Common/CommandResults.cs`, `Common/ZoneAuthority.cs`: Economy와 공유하는 요청 결과·소유권 확인
- 각 파일 270줄 아래. 이전 이력의 762줄 저장소를 책임별로 나눴다

## 지킨 것 (이번 저장소의 개선)
- 칸 번호 음수 금지 CHECK, 복합 외래 키(58).
- 획득의 멱등 규칙(저장된 결과, 본문 해시, `REQUEST_MISMATCH`).
- Zone 요청 키는 digest라 Backend는 불투명한 16바이트로 다룬다.

## 검증
- .NET 테스트: 단위 13, EventWorker 17, 통합 65 → 77(새 12). 빌드 경고 0, `dotnet format --verify-no-changes` 통과.
- 새 통합 테스트
  - 확정: 같은 버전 동의 시 한 번 이동, 동시 동의의 단일 확정, 가득 찬 두 인벤토리의 1대1 맞교환(주차 칸), 확정 중 거절 시 금화·아이템 불변, 금화·용량·낡은 Zone 거절, 다른 Zone으로 간 상대
  - 협상: 바뀐 제안이 동의를 지우고 낡은 버전 거절, 캐릭터당·아이템당 열린 거래 하나, 취소가 모두 풀고 닫힌 거래는 다음 단계 거절, 서로 동시에 열어도 교착 없이 하나, 재전송은 저장된 결과·다른 본문은 거절, 만료된 거래는 다음 조작이 닫음
- `tests/integration/README.md`의 거래 시나리오 행을 갱신했다.

## 남긴 것
- 확정 상대의 소유권 세대는 비교하지 않는다. 세대는 캐릭터마다 따로 세므로, 호출자는 인스턴스와 세대를 모두 맞춰야 하고 상대는 같은 살아 있는 Zone 인스턴스에 있으면 된다.
- 취소는 현재 소유자만 할 수 있다. Zone은 이동 전에 취소한다(60).
- 제안당 아이템 수 상한은 두지 않았다. 너무 큰 제안은 확정에서 `INVENTORY_FULL`로 거절된다.
- 원장의 `item_transferred`는 받는 쪽에만 쓴다(이전 이력과 같음).

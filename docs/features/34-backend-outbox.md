# 34 (6단계) Backend Outbox: 확정된 처치와 획득이 같은 트랜잭션에 이벤트를 남긴다

## 배경과 목표
영구 자산의 기준은 Backend(.NET)의 PostgreSQL 트랜잭션이다. 처치 보상과 아이템 획득은 호출 하나가 트랜잭션 하나로 확정된다. 6단계는 이렇게 확정된 사실을 다른 프로세스(조회 모델, 이후 랭킹)가 받아 보게 하는 단계다. 그 출발점이 Outbox다. 업무 변경과 같은 트랜잭션에 이벤트 행을 넣으면, "DB에는 반영됐는데 이벤트는 안 나갔다"나 "이벤트는 나갔는데 DB는 롤백됐다"가 생기지 않는다. 행을 Kafka로 내보내는 일은 다음 PR(35)의 EventWorker가 한다.

5단계에서 테이블(`outbox_events`, 집합별 순번 `aggregate_sequences`)은 만들어 두었고, 33에서 처치 이벤트 계약(`KillRecorded`)을 더했다. 이 PR은 Backend가 실제로 행을 쓰게 한다.

완료 조건: 처치 기록과 획득이 커밋될 때마다 이벤트 행이 정확히 하나 생기고, 거절·재시도·경쟁에서 진 요청은 행을 남기지 않으며, 캐릭터마다 순번이 1부터 빈틈없이 오른다. 통합 테스트로 DB 행을 단언한다.

## 고민한 선택지와 결정
| 주제 | 선택지 | 결정 |
|---|---|---|
| 이벤트를 쓰는 자리 | 트랜잭션 커밋 뒤 Kafka에 바로 / 같은 트랜잭션에 Outbox 행 | Outbox 행. 커밋과 발행 사이에 프로세스가 죽어도 행이 남아 나중에 나간다. 발행은 적어도 한 번이고, 중복은 소비자의 Inbox가 거른다 |
| 쓰는 코드의 자리 | Economy 모듈 안 / 공용 인프라 | 공용(`Infrastructure/Outbox`). 9단계 거래도 같은 방식으로 쓴다. 한 모듈의 내부를 다른 모듈이 참조하지 않는다 |
| 순번 할당 | 시퀀스 객체 / 집합별 행의 upsert | 집합별 행(`INSERT ... ON CONFLICT DO UPDATE ... RETURNING`). 행 잠금이 커밋까지 유지돼 한 집합의 쓰기가 줄 서고, 롤백되면 순번도 돌아가 빈틈이 없다. 전역 시퀀스는 롤백돼도 값을 되돌리지 않아 소비자가 빈틈을 유실로 오해한다 |
| 이벤트 종류 이름 | 문자열 상수 / protobuf 메시지 이름 | 메시지 이름(`Descriptor.Name`). 소비자가 봉투만 보고 파서를 고를 수 있고, 이름이 두 곳에서 어긋날 일이 없다 |
| 원인 키 | 비움 / 원인 요청의 멱등성 키 | 처치는 처치 ID, 획득은 Zone이 보낸 요청 키. 이벤트 하나를 그 원인까지 거슬러 볼 수 있다 |
| 집합 지정 | 종류 문자열과 원시 `long` / 타입 있는 값 | `EventAggregate.Character(CharacterId)`. 원시 ID를 인자로 넘기지 않는다 |

## 구현
- `Infrastructure/Outbox/OutboxWriter.cs`: `EventAggregate`, `OutboxEvent`(월드, 집합, 메시지, 원인 키), `OutboxWriter.AppendAsync`(호출자의 트랜잭션 안에서 순번 할당과 행 쓰기, 스키마 버전 1)
- `Modules/Economy/EconomyRepository.cs`
  - 처치 기록: 지갑 입금 직후 `KillRecorded`(캐릭터, 처치 ID, 몬스터, 지급 골드, 잔액, 드롭). 반향(이미 기록된 처치)에서는 쓰지 않는다
  - 획득: 아이템을 칸에 넣고 인벤토리 버전을 올린 뒤 `InventoryItemAcquired`(캐릭터, 아이템, 템플릿, 인벤토리 버전). 가방 가득·이미 가져감·모르는 아이템은 결과만 저장하고 이벤트는 쓰지 않는다
- 테스트 하네스: `Db.QueryAsync`, `Db.OutboxOfCharacterAsync`
- 통합 테스트 단언 추가(새 테스트는 없다)
  - 처치와 그 재시도: 행 하나, 순번 1, 원인 = 처치 ID, 내용(캐릭터·몬스터·골드·잔액·드롭)
  - 낡은 권한의 처치: 행 없음
  - 여덟 명의 동시 획득: 획득 이벤트 하나
  - 처치 → 획득 → 재시도 → 같은 ID 다른 본문: 순번 1, 2만, 원인 = 요청 키
  - 가득 찬 가방: 획득한 만큼만 이벤트, 순번에 빈틈 없음
  - 같은 요청 두 개가 동시에: 획득 이벤트 하나
- README: 자산 절에 이벤트 항목, 프로세스 구성도의 Infrastructure. 설계 노트 07의 "아직 안 한 것"

## 옮기면서 고친 것
- 이전 이력은 집합을 종류 문자열과 원시 `long` 두 인자로 넘겼다. `EventAggregate`로 묶고 캐릭터용 생성자를 두었다.
- 이전 쓰기 함수는 쓰지 않는 순번을 돌려줬다. 반환값을 없앴다.
- 이전 테스트는 처치·획득·경쟁만 봤다. 거절(가득 찬 가방)과 같은 요청의 동시 중복에서 이벤트가 생기지 않는다는 단언, 순번에 빈틈이 없다는 단언, 낡은 권한에서 행이 없다는 단언을 더했다.
- 이전 주석의 설계 문서 절 번호는 지우고 이유를 그 자리에 적었다.

# 22 (5단계) Backend 경제 모듈: 처치 보상과 획득을 한 트랜잭션으로

## 배경과 목표
21에서 자산 테이블과 Economy 계약을 깔았다. 이 PR은 그 계약을 Backend에 구현한다. Zone이 보고한 처치를 기록해 드롭과 골드를 주고, 바닥의 아이템을 인벤토리로 옮기고, 캐릭터의 자산을 조회한다. 핵심은 경합과 재시도다. 여러 캐릭터가 한 아이템을 동시에 집거나, 응답을 못 받은 Zone이 같은 요청을 다시 보내거나, 소유권을 잃은 Zone이 늦게 보고해도 자산이 두 번 생기거나 사라지면 안 된다. Zone이 이 호출을 실제로 쓰는 것은 다음 PR이다. 완료 조건: `tests/integration/README.md`의 5단계 시나리오(동시 획득, 요청 중복, ID 오용, 응답 유실)를 포함한 통합 테스트가 실제 PostgreSQL에서 DB 상태로 통과한다.

## 고민한 선택지와 결정
| 주제 | 선택지 | 결정 |
|---|---|---|
| 판정 위치 | 읽고 나서 코드에서 판단 / 트랜잭션 안의 조건부 문장과 제약 | 조건부 문장과 제약. 영수증과 요청 결과는 `INSERT ... ON CONFLICT DO NOTHING`으로 넣은 쪽만 진행하고, 아이템 이동은 "아직 소유 Zone의 바닥에 있으면"을 조건으로 건 UPDATE다. 읽고 판단하는 사이에 다른 트랜잭션이 끼어들 틈이 없다 |
| 호출자 확인 | Zone이 보낸 값을 믿음 / 소유권 행과 대조 | 대조. 요청에 Zone 인스턴스와 `owner_epoch`를 싣고 소유권 행과 같아야 한다. 그 행에 공유 잠금을 걸어, 확인과 지급 사이에 소유권이 바뀌지 못하게 한다 |
| 재시도의 답 | 다시 계산 / 저장된 결과 | 저장된 결과. 처치는 같은 `kill_id`면 저장된 드롭을 돌려주고 아무것도 더 주지 않는다. 획득은 요청 결과에 응답 전체를 저장하고 본문 해시로 같은 ID의 다른 요청을 거절한다 |
| 빈 칸 선택 | 아무 빈 칸 / 가장 앞 빈 칸 | 가장 앞 빈 칸. 캐릭터의 인벤토리 행을 잠가 한 캐릭터의 획득을 줄 세운 뒤 고른다. 칸이 빽빽해 클라이언트 표시가 단순하다 |
| 골드의 출처 | Zone이 금액을 보냄 / 드롭 표에서 Backend가 계산 | 드롭 표. Zone은 아이템 굴림 결과만 보내고, 골드는 Backend가 같은 game-data에서 읽는다. 콘텐츠 버전이 다르면 처치를 거절한다 |
| 콘텐츠 읽기 | Backend에 수치를 따로 둠 / 같은 game-data를 Tomlyn으로 | 같은 game-data. Zone과 Backend가 한 리비전을 본다(`Economy:ContentDir`) |

## 구현
- 계약: 처치 골드를 드롭 표에서 정하도록 `RecordKill`을 고쳤다
- `GameBackend/Common/OpaqueId`: 16바이트 ID 도우미를 모듈 사이에서 공유. ID마다 강타입 래퍼는 그대로다
- `Modules/Economy`: `ContentCatalog`(game-data 읽기), `EconomyRepository`(트랜잭션), `EconomyGrpcService`, `EconomyModule`, `EconomyOptions`, `Ids`
- 통합 테스트 7개(아래 검증), 하네스의 Economy 클라이언트·입장 도우미·테스트 콘텐츠
- `scripts/e2e-local.sh`, `scripts/dev-stack.sh`: Backend에 저장소 루트 기준의 game-data 경로를 넘긴다
- 패키지: Tomlyn 2.10.1. 잠금 파일을 패키지가 들어온 커밋마다 함께 갱신했다(아래 문제)
- README: 구조 표·프로세스 내부·데이터의 기준·데이터 모델 그림에 경제 모듈과 테이블, "자산과 멱등성"에 Backend 동작, 검증 절의 통과 목록
- CONTRIBUTING: 패키지를 바꾸면 잠금 파일을 같은 커밋에서 갱신한다

## 만난 문제
- [011](../issues/011-backend-content-dir-resolved-inside-its-own-directory.md) PR 전 end-to-end에서 Backend가 시작하자마자 죽었다. 스크립트가 Backend 디렉터리로 `cd`한 뒤 `$PWD/game-data`를 넘겼다. 이전 이력은 다음 피처 안에서 고쳤으니, 이 피처는 스크립트가 깨진 채 병합됐던 것이다. 그 수정 커밋을 당겨 왔다.
- 이전 이력에는 패키지 잠금 파일이 없었다. 이 저장소는 06부터 잠금 파일을 쓰고 CI가 `--locked-mode`로 복원한다. 커밋을 그대로 옮기면 Tomlyn이 잠금 파일에 없어 NU1004로 .NET 잡이 실패한다. 푸시 전에 로컬 잠금 모드 복원으로 확인하고, 잠금 파일을 마지막에 한 번만 고치는 대신 패키지가 들어온 커밋마다 그 시점의 잠금 파일을 합쳤다. "커밋마다 빌드된다"를 잠금 모드에서도 지키기 위해서다. 이 브랜치의 모든 커밋에서 잠금 모드 복원이 통과한다.
- 자동 치환이 처치 보상 절(설계 문서 8.2)을 "전투"로 바꿨다. 보상은 "자산과 멱등성"이다. 손으로 고치고 치환 표에 8.2를 따로 넣었다. 숫자만 남은 `(10.2)`도 지웠다.

## 검증
- .NET: 경고 0, 단위 4개, 통합 33개 통과(21보다 7개 늘었다), `dotnet format` 통과. 새 통합 테스트:
  - 여러 캐릭터가 한 아이템을 동시에 집으면 정확히 하나만 얻는다
  - 재시도는 저장된 결과를 받고, 같은 ID의 다른 본문은 거절된다
  - 아이템은 그 캐릭터를 소유한 Zone을 통해서만 집을 수 있다
  - 인벤토리가 차면 다음 아이템을 거절하고, 칸은 빽빽하다
  - 처치는 아이템과 골드를 한 번만 주고, 재시도는 아이템을 되돌려줄 뿐 다시 주지 않는다
  - 소유권 세대가 낡은 Zone의 처치는 아무것도 주지 않는다
  - 다른 콘텐츠 버전이나 드롭 표가 허용하지 않는 드롭은 거절된다
- 잠금 모드 복원: 브랜치의 모든 커밋에서 통과.
- C++: dev 142개 통과, clang-tidy 경고 0, ASan·UBSan 142개 통과, 형식 검사 통과. C++ 코드는 바뀌지 않았고 계약만 바뀌었다.
- end-to-end(스크립트 수정 뒤): 기본은 봇 5개 전원 입장·모순 0·남은 세션 0. 전투는 봇 6개, 시전 수락 48·거절 0, 처치 14, 봇 사망 0, 모순 0. 대화형 스택도 Backend가 정상으로 뜬다.

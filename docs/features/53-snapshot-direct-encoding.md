# 53 (8c) 스냅샷 직접 인코딩, 그리고 측정으로 뺀 작업자 풀

## 배경과 목표
이 프로젝트의 Zone(C++)은 100 ms마다 플레이어마다 스냅샷을 만든다. 지금까지는 스냅샷마다 protobuf 메시지 객체를 만들었다. 보이는 엔티티마다 하나씩이고 1,000명이면 수십만 개다. 그 뒤 다시 직렬화해 Gateway 링크에 썼다. 8b 뒤 1,000명에서 Zone 스레드는 0.61코어를 썼고, 그중 호스트 전달(시야 수집·직렬화·링크 쓰기)이 0.28코어였다(보고서 03).

이전 이력은 이 자리에 두 가지를 넣었다.
- 메시지 객체 없이 와이어 형식으로 바로 쓰는 인코더
- 인코딩을 작업자 스레드에 나누는 작업자 풀

이 PR은 둘을 51의 예산 판단과 함께 넣으려고 시작했다. 재 보니 작업자 풀은 이득이 없어서 뺐다.

완료 조건:
- 직접 인코더가 protobuf 경로와 바이트 단위로 같다.
- 51의 링크별 예산과 오래 기다린 세션 우선이 그대로다.
- 1,000명에서 Zone CPU가 측정으로 준다.

## 고민한 선택지와 결정
| 주제 | 선택지 | 결정 |
|---|---|---|
| 직렬화 | protobuf 메시지 객체 / 와이어 형식에 직접 | 직접. 크기를 먼저 계산하고 한 번에 쓴다. 필드 번호는 생성된 클래스에서 가져와 계약이 바뀌면 드러난다 |
| 실수 0의 생략 | `value == 0.0F` / 비트 패턴 | 비트 패턴. protobuf는 비트가 0이 아닌 값(-0.0 포함)을 직렬화한다. 이전 이력의 인코더는 -0.0을 생략해 서쪽으로 걷는 엔티티의 속도에서 바이트가 달라질 수 있었다 |
| 인코딩 병렬화 | 작업자 풀(이전 이력) / 하지 않음 | 하지 않음(측정). 직접 인코딩 뒤 전달 비용이 0.05~0.06코어라 나눌 것이 없다. 풀이 있으면 51의 예산을 "직전 크기로 미리 고르기"로 바꿔야 하는데, 이득 없이 판단만 덜 정확해진다 |
| 미리 직렬화한 전송 | 메시지만 / 바이트도 | 바이트도(`FramedConnection::SendPayload`, `LinkSink::SendPayload`). 결과를 `bool` 대신 `std::expected`로 돌려준다(이전 이력은 `bool`). 다른 프레임처럼 `QueuedBytes()`에 잡혀 51의 예산 판단에 들어간다 |

## 측정 (1,000명, release, 보고서 03과 같은 조건)
| | 51 이후 | 직접 인코딩 + 작업자 4 | 직접 인코딩 + 작업자 0 | 이 PR(풀 없음) |
|---|---|---|---|---|
| Zone CPU (전체) | 0.61 | 0.40~0.41 | 0.40 | **0.39** |
| 그중 호스트 전달 | 0.28 | 0.04~0.05 | 0.06 | **0.05** |
| 그중 시뮬레이션 | 0.32 | 0.31~0.32 | 0.32 | 0.32 |
| Zone 메모리 | 45 MiB | 58 MiB | 57 MiB | **45 MiB** |
| 놓친 틱 / 미룬 스냅샷 | 0 / 0 | 0 / 0 | 0 / 0 | 0 / 0 |

- 500명은 Zone 0.22코어에서 **0.13코어**가 됐다.
- 작업자 4개와 0개가 같다. 인코딩이 싸져 나눌 일이 남지 않았다.
- 풀 버전의 메모리가 더 큰 것은 틱마다 모든 시야와 결과를 동시에 들고 있어서다. 지금은 한 번에 하나만 들고 인코딩 즉시 보낸다.
- 이제 1,000명에서 가장 바쁜 것은 시뮬레이션(0.32)과 Gateway(0.49)다. 54에서 틱 단계별 시간을 재서 관심 계산이 병목이고 병렬화로 줄면, 그때 작업자 풀을 그 근거로 넣는다.

## 구현
- `zone/server/snapshot_encoder.{hpp,cpp}`: `EncodeSnapshotOutput(session_id, view, tick, out)`. `ZoneToGateway{session_output{id, ServerMessage{world_snapshot}}}`를 크기 계산 → 한 번 쓰기로 만든다. 계산과 쓰기가 다르면 즉시 중단한다(프로그래밍 오류).
- `ZoneHost::SendSnapshots`: 51의 흐름 그대로(오래된 순, 예산 확인, 수집, 전송). 직렬화만 직접 인코더로 바꿨다. 결과 문자열 하나를 재사용한다.
- `codec::NonNegative`: 체력·마나의 부호 처리를 인코더와 공유한다(이전의 내부 `Clamped`).
- `FramedConnection::SendPayload`, `LinkSink::SendPayload`, `GatewayLink::SendPayload`
- `cmake/Sanitizers.cmake`: TSan 빌드에 `-Wno-tsan`. 아래 "만난 문제".

## 지킨 것 (이번 저장소의 개선)
- 51의 링크별 예산, 오래 기다린 세션 우선, 시야 상한·진입 분할. 예산은 실제로 보낸 바이트로 판단한다.
- 50의 `QueuedBytes()`: 미리 직렬화한 프레임도 같은 쓰기 경로라 대기 바이트에 잡힌다.
- 오류는 타입으로(`SendPayload`의 `std::expected`).

## 옮기면서 고친 것
- -0.0 처리를 protobuf와 맞췄다. 테스트가 -0.0 속도를 넣어 바이트 일치를 확인하고, protobuf가 -0.0을 실제로 쓴다는 것도 크기로 확인한다.
- `SendPayload`의 반환을 `bool`에서 `std::expected`로 바꿨다.
- 이전 이력의 작업자 풀은 측정으로 뺐다. 옮겼다면 쓰는 곳 없이 메모리만 늘리는 추상화였다.

## 만난 문제
- TSan 프리셋이 빌드되지 않았다. GCC 14가 asio의 `atomic_thread_fence`에 `-Wtsan` 경고를 내고, `-Werror`가 그것을 오류로 바꿨다. TSan 빌드에만 `-Wno-tsan`을 더했다.
- 그 뒤 TSan으로 작업자 풀 경로(실제 작업자 3개로 인코딩해 인라인 결과와 바이트 비교)를 30번 돌렸다. 데이터 경합 보고는 0건이었다. 다만 스레드를 쓰지 않는 테스트에서도 protobuf 메시지 복사 안에서 heap-use-after-free 보고가 났다. vcpkg의 protobuf는 TSan 계측 없이 빌드됐다. 같은 테스트가 ASan에서 깨끗하므로 계측되지 않은 할당에서 생긴 오탐으로 보고, Sanitizers.cmake 주석에 적었다. 작업자 풀은 결국 뺐지만 TSan 프리셋은 쓸 수 있게 남긴다.

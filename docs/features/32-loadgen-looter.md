# 32 (5단계) 획득 봇: 떨어진 아이템을 줍는 Looter와 획득 end-to-end

## 배경과 목표
21~24로 처치 보상과 아이템 획득이 Backend의 한 트랜잭션으로 확정되고, Zone은 드롭을 굴리고 획득을 예약한다. 하지만 획득은 단위·통합 테스트로만 확인했고, 실제 스택에서 여러 플레이어가 같은 아이템을 노릴 때 깨지지 않는지는 아무도 돌려 보지 않았다. 이 PR은 아이템을 줍는 봇과 그 봇이 획득해야 통과하는 end-to-end 프로필, 뷰어의 획득 조작, 그리고 자산 설계 노트를 더한다. 이것으로 5단계(자산과 멱등성)가 끝난다.

완료 조건: `looters.toml`로 돌린 end-to-end가 정해진 수 이상의 처치와 획득을 Backend DB에서 확인하고, 정합성 오류 0으로 통과한다.

## 고민한 선택지와 결정
| 주제 | 선택지 | 결정 |
|---|---|---|
| 획득 두뇌 | 획득만 하는 봇 / 아이템이 없으면 사냥하는 봇 | 사냥도 한다(`LooterParams.fight`). 아이템은 처치에서만 생기므로, 줍기만 하는 봇은 전투 봇이 같이 돌아야 의미가 있다. 혼자서도 드롭을 만들고 주워야 프로필 하나로 끝난다 |
| 재요청 간격 | 틱 수로 설정 / 벽시계 시간으로 설정 | 시간(`pickup_retry_ms`). 봇은 서버의 틱 레이트를 Welcome에서 배운다. 공격 간격과 같은 방식으로 틱으로 바꾼다(`TicksCovering`, 전투 봇과 공유) |
| 결과의 분류 | 결과를 상태로만 센다 / 요청 ID마다 종류를 기억 | 종류를 기억한다(`RequestKind`). 시전과 획득이 같은 `CommandResult`로 오므로 상태만 보면 어느 쪽의 수락인지 모른다 |
| `PENDING` | 결과로 센다 / 최종 판정까지 무시 | 무시. 획득은 대기 뒤 최종 판정이 한 번 더 온다. 대기를 세면 요청 하나가 두 번 집계된다 |
| 모순으로 볼 것 | 상태만 집계 / 보낸 적 없거나 이미 답을 받은 요청의 결과, 뒤로 간 인벤토리 버전도 센다 | 센다. 서버는 요청마다 최종 답 하나, 인벤토리는 버전 순서를 약속했다 |
| 판정 근거 | 봇이 센 획득 / DB 원장 | 둘 다. 봇의 `min_pickups`와 함께, 스크립트가 이 실행 뒤로 생긴 원장의 `item_acquired` 행을 센다. 처치를 영수증으로 확인하는 것과 같은 이유다 |
| 뷰어의 획득 거리 | 코드에 2.0 / game-data에서 읽기 | `game-data/rules/economy.toml`의 `[pickup] range_m`을 읽는다. 맵 장애물을 읽는 것과 같은 방식이다. 숫자를 복제하면 데이터가 바뀔 때 뷰어만 틀린다 |

## 구현
- `tools/loadgen/bot`: `Looter`(보이는 가장 가까운 아이템으로 가서 획득 거리 안이면 요청하고, 같은 아이템은 재요청 간격 뒤에 다시. 없으면 `Fighter`처럼 사냥), `SeenKind::kItem`, `Intent.pickup`, 공용 `TicksCovering`. 서버 틱 레이트를 모르는 동안(입장 전)은 아무것도 하지 않는다
- `tools/loadgen/client`
  - 프로필: `bots.looters`, `run.min_pickups`, `[looter] loot_radius_m · pickup_range_m · pickup_retry_ms`. 역할은 `BotRole`/`RoleOf`(배회 → 전투 → 획득 순 번호). 판정 기준은 `PassCriteria` 하나로 묶었다. 역할 수의 합은 64비트로 더해 넘침을 거절한다
  - 월드 모델: `ExpectResult(RequestId, RequestKind)`, 종류별 집계(시전 수락·거절·미확정, 획득·거절·미확정), `OnInventoryUpdate`(아이템 수·골드, 버전 역행은 모순), `awaiting_results()`, 떨어진 아이템을 `kItem`으로
  - 세션: 시전·획득을 보내기 전에 요청 ID와 종류를 등록하고, `PickupItem`을 보낸다
  - 보고서: 획득 요청·획득·거절·미확정, 보유 아이템과 골드, `min_pickups` 판정
  - `profiles/looters.toml`(획득 5 + 배회 1, 40초, 처치 2·획득 1 이상). smoke·fighters에 새 키(획득 봇 0)
- `scripts/e2e-local.sh`: 프로필의 `min_pickups`만큼 원장의 획득 행이 있는지 검사
- `tools/viewer`: F 키 획득, `CommandResult`의 대기·미확정·최종 구분, HUD의 인벤토리(개수/용량, 버전, 골드)와 아이템 줄, 버전이 뒤로 간 인벤토리는 모순으로 센다
- 설계 노트 07 자산과 멱등성: 누가 무엇을 결정하나, 동시 획득, 요청 중복, 응답 유실, 낡은 Zone, DB 제약
- README: loadgen·뷰어 표, 자산 절의 노트 링크, 검증의 모순 목록과 획득 end-to-end, 빌드 명령. CLAUDE.md에 5단계 완료
- 테스트 8개: Looter 4개, 월드 모델 3개(종류별 집계와 대기 무시, 모르는 요청과 중복 답, 인벤토리 버전), 프로필 1개(획득 설정·역할 수 넘침), 보고서 1개(획득 기준). 대기·미확정 결과 테스트 1개는 종류별 집계 테스트로 바뀌었다

## 옮기면서 고친 것
이전 이력의 같은 피처를 옮기며 다시 봤다.
- 이전 `LooterParams`는 기본값이 있었고 재요청 간격이 틱 수였다. 기본값을 없애고(설정이 늘 채운다) 간격을 `std::chrono`로 바꿨다.
- 이전 프로필은 역할 수를 32비트로 더해, 큰 값이 넘쳐 작은 봇 수처럼 보일 수 있었다.
- 이전 월드 모델은 시전의 미확정(`UNKNOWN`)을 거절로 셌다. 25에서 정한 대로 미확정은 거절이 아니므로, 획득과 같은 규칙으로 따로 센다.
- 이전 end-to-end는 획득을 봇의 집계로만 판정했다. 처치처럼 DB 원장으로도 확인한다.
- 이전 뷰어는 획득 거리를 코드에 적었고(2.0), 미확정 결과를 거절처럼 보였다.
- 이전 설계 노트는 요청 키를 "캐릭터 ID와 요청 ID를 이어 붙인 것", 재시도 기억을 "32개"로 적고, 답이 없을 때 Zone이 곧바로 미확정을 돌려준다고 설명했다. 지금 코드는 소유권 세대를 넣은 다이제스트이고, 기억 크기는 계약 상수이며, 정해진 횟수까지 다시 보낸 뒤 자산을 다시 읽는다. 그에 맞춰 다시 썼고, 측정치는 이 저장소에서 잰 값으로 바꿨다.

## 만난 문제
- 이전 커밋을 그대로 가져오려 하자 부하 생성기 쪽이 충돌투성이였다. 그사이 25(판정 하네스), 29(엄격한 설정), 30(타입 있는 단위)이 같은 파일을 많이 바꿨기 때문이다. 가져오기를 취소하고 이전 변경을 참고해 지금 코드에 직접 옮겼다.

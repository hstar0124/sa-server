# 46 (8단계) Traveler 봇과 뷰어 포털

## 배경과 목표
8단계는 두 번째 Zone과 소유권 이전이다. 지금까지 이렇게 왔다.
- 42~45: 이전 경로를 끝까지 만들었다. 포털 반경에서 `ChangeZone`을 보내면 출발 Zone이 Backend에 이전을 요청한다. Backend는 한 트랜잭션에서 소유권과 세대를 옮긴다. Gateway가 세션을 도착 Zone에 다시 붙이고, 클라이언트는 도착 Zone의 Welcome으로 옮겨졌음을 안다.

이 PR은 그 경로를 쓰는 두 클라이언트다.
- loadgen: 시드 기반 봇 클라이언트(ADR-0006). 두뇌(`sa::bot`)는 네트워크를 모르고, 실행 파일이 Gateway에 접속해 두뇌를 구동한다.
- 뷰어(`tools/viewer`): 사람이 브라우저로 접속해 보는 개발용 클라이언트.

완료 조건:
- 봇이 두 Zone 사이를 오가고, 실행 판정에 넘어간 횟수가 들어간다.
- 뷰어에서 포털이 보이고, 그 안에서 G를 누르면 다음 Zone으로 넘어가 화면이 바뀐다.

## 고민한 선택지와 결정
| 주제 | 선택지 | 결정 |
|---|---|---|
| 다시 묻기 | 매번 새 요청 ID / 결정될 때까지 같은 ID | 같은 ID. 프로토콜이 클라이언트에 요구하는 것이다. "모름" 뒤에 새 ID로 물으면 Zone(45)은 새 이전 ID를 만든다. 첫 시도가 커밋했다면 권한 없음으로 세션이 끝난다. 그래서 두뇌는 "떠나고 싶다"만 말하고, 요청 ID는 세션이 정한다 |
| 포털 접근 | 반경의 절반까지(옛 코드의 `* 0.5`) / 프로파일 값 | 프로파일 값(`traveler.portal_approach_m`). 클라이언트가 보는 위치는 Zone보다 늦다. 그래서 테두리에서 물으면 반경 밖이라고 거절될 수 있다 |
| 시간 | 틱 수 / 벽시계 ms를 서버 틱으로 | 벽시계 ms. 다른 두뇌와 같다. Zone마다 틱을 따로 세므로 도착하면 그 Zone의 시계로 다시 잰다 |
| 새 Zone의 입력 번호 | 1부터 다시 / 계속 올림 | 계속 올린다. 도착 Zone은 새 플레이어의 마지막 입력을 0으로 두므로 어느 쪽이든 받는다. 다시 세면 세션 쪽 상태만 늘어난다. 확인 번호는 월드 모델이 0부터 다시 본다 |
| 뷰어 장애물 | 시작할 때 zone-1 지도 한 번 / Zone이 바뀔 때 그 Zone의 지도 | 그 Zone의 지도(`game-data/maps/zone-<id>.toml`). Zone 설정이 지도 파일을 이렇게 부른다 |

## 구현
- `common/ids.hpp`: `PortalId`. 시뮬레이션과 봇이 같은 타입을 쓰도록 `sim`에서 옮겼다
- `sa::bot`
  - `SeenPortal`, `Observation.portals`·`zone`, `Intent.change_zone`
  - `Traveler`: 배회 → 가장 가까운 포털 → 요청 → 대기(재요청 간격) → 새 Zone에서 다시 배회
- loadgen 클라이언트
  - `WorldModel`: 두 번째 Welcome은 새 Zone이다. 보이던 것을 비우고, 포털·Zone ID를 바꾸고, 확인 번호를 0부터 다시 본다. 이전 결과는 따로 센다(`Travel`)
  - `BotSession`: 결정되지 않은 이전 요청 ID를 기억해 다시 보낸다. 수락·거절이나 새 Welcome에서 잊는다
  - 프로파일: `bots.travelers`, `run.min_zone_changes`, `[traveler] dwell_ms·request_retry_ms·portal_approach_m`. 보고서와 판정에 Zone 이동 횟수가 들어간다
  - `profiles/travelers.toml`: 트래블러 5 + 배회 1, 60초, 이동 5번 이상
- 뷰어
  - 포털을 실제 반경의 파란 원과 목적지 표시로 그린다
  - G로 이동을 요청한다. 결정 전에 다시 누르면 같은 요청 ID로 보낸다
  - 새 Welcome에서 엔티티·포털·장애물을 그 Zone으로 바꾼다. HUD에 Zone을 표시한다
- README: loadgen 역할, 뷰어 조작, loadgen README의 프로파일과 재요청 규칙

## 옮기면서 고친 것
- 이전 이력의 봇과 뷰어는 다시 물을 때마다 새 요청 ID를 썼다. 45에서 고친 서버 쪽 문제를 클라이언트가 다시 일으키는 셈이었다. 결정될 때까지 같은 ID를 쓴다.
- 이전 이력의 뷰어는 Zone 2로 넘어가도 Zone 1의 장애물을 그렸다.
- 이전 이력은 포털까지 걸어갈 거리를 `반경 * 0.5`로 코드에 박아 두었다. 프로파일 값이다.
- 이전 이력은 포털 ID를 원시 `uint32`로 넘겼다. `PortalId`·`ZoneId` 강타입이다.
- 이전 이력은 새 Zone에서 입력 번호를 1로 되돌렸다. 필요 없는 상태 변경이라 뺐다.

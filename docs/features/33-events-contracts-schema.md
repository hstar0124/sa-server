# 33 (6단계) 이벤트 계약과 소비 쪽 스키마: 처치 이벤트, Inbox, 조회 모델

## 배경과 목표
6단계는 확정된 업무 변경을 이벤트로 내보내고, 다른 프로세스가 그것을 한 번씩만 적용해 조회 모델을 만드는 단계다. 이 프로젝트에서 영구 자산의 기준은 Backend(.NET)의 PostgreSQL 트랜잭션이다. 5단계에서 이미 Outbox 테이블(`outbox_events`, 업무 변경과 같은 트랜잭션에 쓰는 이벤트 행)과 집합별 순번(`aggregate_sequences`)을 만들어 두었다. 이 PR은 그 나머지 바탕을 깐다. 처치 이벤트의 계약, 소비자가 이벤트를 한 번만 적용하게 하는 Inbox 테이블, 첫 조회 모델인 캐릭터 통계 테이블이다.

이어지는 PR에서 Backend가 경제 트랜잭션 안에서 Outbox 행을 쓰고(34), EventWorker가 그것을 Kafka로 발행하며(35), 소비자가 조회 모델을 갱신한다(36).

완료 조건: 계약이 C++과 C# 양쪽에서 생성되고, 새 테이블의 규칙을 Backend 코드를 거치지 않은 쓰기로 시험한다.

## 고민한 선택지와 결정
| 주제 | 선택지 | 결정 |
|---|---|---|
| 처치 이벤트의 내용 | 처치 ID만 / 영수증·골드·드롭까지 | 영수증과 골드(지급액·입금 뒤 잔액), 떨어진 아이템까지 담는다(`KillRecorded`). 소비자가 Backend DB를 다시 읽지 않고 조회 모델을 만들 수 있어야 한다 |
| 한 번만 적용하는 근거 | Kafka 오프셋만 / 소비자별 Inbox 행 | Inbox(`inbox_events`, 기본 키 `(consumer_name, event_id)`). 발행자가 Kafka 확인 뒤 죽거나 소비자가 오프셋 커밋 전에 죽으면 같은 이벤트가 다시 온다. 업무 변경과 Inbox 행을 한 트랜잭션에 넣으면 두 번째 적용은 키 충돌로 걸러진다 |
| 조회 모델의 순서 근거 | 도착 순서 / 집합 순번 | 행마다 적용한 가장 높은 `aggregate_seq`를 둔다(`last_event_seq`). 순서가 뒤바뀐 이벤트를 소비자가 알아챌 수 있다 |
| 조회 모델의 월드 | `world_id`를 따로 참조 / 캐릭터와 복합 참조 | 복합 FK `(world_id, character_id)` → `characters`. 0005에서 다른 테이블에 건 규칙과 같다. 캐릭터와 다른 월드를 가리키는 통계 행을 DB가 거절한다 |
| Kafka를 compose에 넣는 시점 | 이 PR / 처음 쓰는 발행자 PR | 발행자 PR(35). 이전 이력은 여기서 넣었지만, 쓰는 코드 없이 떠 있는 브로커는 README에 적을 것도 시험할 것도 없다 |

## 구현
- `contracts/events/envelope.proto`: `KillRecorded`(캐릭터, 처치 ID, 몬스터 템플릿, 지급 골드, 잔액, 드롭)와 `DroppedItemRef`. character 집합의 토픽(`game.character-events.v1`)과 키(`world_id:character_id`)를 주석으로
- `database/migrations/0006_events.sql`
  - `inbox_events`: 소비자 이름 형식(소문자·숫자·하이픈), 16바이트 이벤트 ID
  - `character_projections`: 처치·획득·획득 골드·마지막 순번, 음수 금지 CHECK, 캐릭터와 복합 FK
- 통합 테스트 2개: 조회 모델은 캐릭터 자신의 월드만, 음수 거절. 소비자 하나가 같은 이벤트를 두 번 기록하면 거절되고 다른 소비자는 따로 기록한다. 짧은 ID와 빈 소비자 이름 거절
- README: 자산 절의 테이블 표에 두 테이블

## 옮기면서 고친 것
- 이전 이력의 조회 모델은 `world_id`와 `character_id`를 각각 참조해서, 캐릭터와 다른 월드의 행을 만들 수 있었다. 복합 FK로 바꿨다. `last_event_seq`에도 음수 금지를 더했다.
- 소비자 이름에 형식 CHECK를 더했다. 빈 문자열이나 오타 섞인 이름이 Inbox에 따로 쌓이면 같은 이벤트를 두 번 적용한 것과 같다.
- 이전 마이그레이션 번호 0005는 0005(정합성 제약)가 이미 있어 0006이 됐다. 주석의 설계 문서 절 번호는 지우고 이유를 그 자리에 적었다.
- 계약 주석을 파일의 기존 문체(한국어)에 맞췄다.

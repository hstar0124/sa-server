# 54 (8c) dead reckoning과 시야 주기 관심 계산: 1,000명에서 대역폭 92%, Zone CPU 42% 감소

## 배경과 목표
이 프로젝트의 Zone(C++)은 20 Hz로 시뮬레이션하고, 100 ms마다 플레이어마다 스냅샷을 만들어 Gateway로 보낸다. Gateway는 그것을 클라이언트에 전달한다. 스냅샷은 시야(관심 집합) 안 엔티티의 변화분이다. 새로 보이는 엔티티는 spawn, 바뀐 엔티티는 update, 사라진 엔티티는 despawn으로 간다. 53 뒤 1,000명에서의 상태는 다음과 같았다.
- Zone 0.38코어, 그중 시뮬레이션 0.31코어
- Gateway 0.49코어로 가장 바쁜 프로세스
- Zone→Gateway 37 MiB/s, 스냅샷 하나에 3.8 KB

이유는 둘이었다.
- 걷는 엔티티는 틱마다 위치가 바뀌니 시야 안의 모두가 스냅샷마다 update로 다시 갔다.
- 시뮬레이션 시간이 어디에 쓰이는지 몰랐다.

이 PR은 먼저 틱 단계별 시간을 재고, 그 숫자로 고칠 곳을 정했다.

완료 조건:
- 단계별 시간과 스냅샷 바이트가 통계 줄과 용량 벤치에 나온다.
- 직진하는 엔티티는 한 번만 보고된다. 봇과 뷰어는 보고된 속도로 외삽한다.
- 1,000명에서 대역폭과 CPU가 측정으로 준다. 정합성 오류 0, 스냅샷 수가 같다.

## 고민한 선택지와 결정
| 주제 | 선택지 | 결정 |
|---|---|---|
| 무엇부터 | 바로 최적화 / 단계별 시간 먼저 | 시간 먼저. 시뮬레이션 0.31코어 중 **관심 계산이 0.30**이었고 나머지 단계는 다 합쳐 0.01이었다. 이 숫자가 아래 결정의 근거다 |
| 움직임 보고 | 위치가 바뀌면 매번 / dead reckoning | dead reckoning. 클라이언트는 위치 + 속도 × 경과 시간으로 외삽하고, Zone은 그 추정이 틀릴 때만 다시 보낸다. 속도가 `sync.publish_velocity_delta_mps`(0.25 m/s)보다 바뀌었거나, 실제 위치가 외삽에서 `sync.publish_position_error_m`(0.1 m)보다 벗어났을 때다. 0.25 m/s는 걷기 속도 6 m/s에서 약 2도 꺾임이다 |
| 보고하는 속도 | 의도한 속도 / 실제로 이룬 속도 | 이룬 속도. 벽을 따라 미끄러지면 의도(대각선)와 실제(벽과 나란히)가 다르다. 의도를 보내면 모든 관찰자 화면에서 벽 속으로 들어간다 |
| 관찰자에게 보낼 변화 | 체력·MP·이동 모두 / 관찰자가 보는 것만 | 보는 것만. EntityUpdate에는 MP가 없는데 MP 회복과 시전 비용이 `changed_at`을 찍어 update를 만들고 있었다. 자기 MP는 매 스냅샷의 `self_vitals`로 간다 |
| 관심 계산 주기 | 매 틱(20 Hz) / 시야를 모으는 틱만(10 Hz) | 시야 틱만(`ZoneConfig::ticks_per_view`, 호스트의 스냅샷 주기). 관심 집합은 시야 수집만 읽으니 그 사이의 계산은 버려졌다 |
| 관심 계산 병렬화 | 작업자 풀(이전 이력) / 하지 않음 | 하지 않음. 53에서 측정으로 풀을 뺐다. 주기를 반으로 줄인 뒤 관심 계산은 0.15코어라 지금 나눌 이유가 없다 |
| 전투 이벤트 수신자 | 관심 집합 / 클라이언트가 아는 집합(`known`) | known. 51에서 새 엔티티를 시야당 32개씩 나눠 보내므로, 관심 집합에는 있지만 아직 spawn을 받지 않은 엔티티가 있다. 그 엔티티에 대한 이벤트는 클라이언트가 보여 줄 수 없다 |
| 관심 계산 사이에 떠난 엔티티 | 다음 계산까지 둔다 / 시야 수집에서 거른다 | 거른다. 관심 집합이 계산된 뒤 떠난 엔티티는 시야에서 despawn으로 바로 나간다 |

## 측정 (1,000명, release, 각 2회)
| | 53 이후(기준선) | + dead reckoning | + 시야 주기 관심 계산 |
|---|---|---|---|
| Zone CPU | 0.38 | 0.36~0.37 | **0.22** |
| 그중 시뮬레이션 / 관심 계산 | 0.31 / 0.30 | 0.30~0.31 / 0.30 | **0.15~0.16 / 0.15** |
| 그중 호스트 전달 | 0.05 | 0.03 | 0.03 |
| Gateway CPU | 0.49 | **0.23** | 0.22~0.23 |
| Zone→Gateway | 37 MiB/s | **2.8 MiB/s** | 2.7~3.0 MiB/s |
| 스냅샷 하나 | 3.8 KB | **290 B** | 270~300 B |
| Zone / Gateway 메모리 | 45 / 53 MiB | 43 / 53 MiB | 43 / 53 MiB |
| 놓친 틱 / 미룬 스냅샷 / 정합성 오류 | 0 / 0 / 0 | 0 / 0 / 0 | 0 / 0 / 0 |

- 스냅샷 수는 세 열 모두 초당 약 10,200개다. 미룬 스냅샷이 0이므로 모든 클라이언트가 초당 10개를 받았다. 같은 스냅샷을 더 적은 바이트와 CPU로 보냈다.
- 봇의 전투 결과(명중 174, 처치 44)도 세 열이 같다. 다만 초원의 몬스터 수가 상한이라 전투량이 이 값에 묶인다. 그래서 이 숫자는 외삽으로 바뀐 봇 행동이 전투를 망치지 않았다는 정도의 근거다.
- Gateway CPU가 절반이 된 것은 dead reckoning 덕이다. Gateway는 링크에서 받은 스냅샷을 클라이언트마다 다시 써 보내므로, 바이트가 줄자 일도 함께 줄었다.
- 링크 대기 최대치도 4 MiB(51의 예산 한도)에서 1.2 MiB로 내려갔다. 이제 예산에 닿지 않는다.

## 구현
- 계약: `EntitySpawn.velocity`(7). spawn만 받고 update가 없는 엔티티도 외삽할 수 있다.
- `game-data/rules/movement.toml [sync]`, `MovementRules::publish_velocity_delta_mps`·`publish_position_error_m`. 로더가 읽고 검증한다(음수, NaN 거부).
- `sim::Zone`
  - `Published{position, velocity, at}`: 관찰자가 외삽하는 기준. 플레이어와 몬스터가 들고 있다.
  - `PublishIfDeviated`: 매 틱 이동 단계 끝에서 플레이어와 몬스터를 검사한다. 서 있는 몸도 검사해서 부활·귀환 같은 순간 이동이 보고된다. `Publish`는 죽음과 부활처럼 바로 알려야 할 때 쓴다.
  - 투사체는 등속 직선이라 발사 때 한 번만 보고한다(`Projectile::changed_at`).
  - `ChangedAt(entity)`: 떠난 엔티티는 값이 없다. 시야 수집이 이것으로 update와 despawn을 함께 정한다.
  - `ZoneConfig::ticks_per_view`: 관심 계산을 그 틱에만 한다. 0은 `Create`가 거부한다. `main`이 스냅샷 주기를 넘긴다.
  - `TickProfile`, `set_profile_clock`, `TakeProfile`: 단계별 시간. 시뮬레이션은 시계를 읽지 않고, 주입된 시계가 있을 때만 잰다.
- `zone/server`: `TickRunner`가 실제 시계를 주입하고 통계 줄 `phases ...`를 남긴다. `ZoneHost::Stats::snapshot_bytes`. 인코더와 `codec`이 spawn 속도를 쓴다.
- `scripts/bench/capacity.sh`: 단계별 코어, 초당 스냅샷, MiB/s, 스냅샷당 바이트.
- loadgen `WorldModel`: 엔티티마다 마지막 보고 위치·속도·틱을 두고, 두뇌에게는 최신 서버 틱으로 외삽한 위치를 준다.
- 뷰어: spawn 속도를 첫 샘플에 넣는다. 샘플이 하나뿐일 때도 외삽한다(전에는 멈춰 그렸다). 근처 몬스터·아이템 고르기도 외삽 위치로 한다. 체크박스 이름은 "갱신 사이 외삽 (dead reckoning)"이다. 끄면 걷는 엔티티가 마지막 보고 위치에 멈춰서, 왜 외삽이 프로토콜의 일부인지 보인다.

## 지킨 것 (이번 저장소의 개선)
- 51의 링크별 예산, 오래 기다린 세션 우선, 시야 상한(128)과 진입 분할(32), 히스테리시스 순위.
- 정지도 변경이다(이전의 `SetVelocity`). dead reckoning에서는 속도 변화 검사가 그 역할을 한다. 테스트 "AStopIsReported..."가 그대로 통과한다.
- 결정적 순서(`IdsInOrder`), 동률은 낮은 id(`KeepNearest`).
- 46의 Zone 변경 처리: 새 Welcome에서 봇의 보이는 집합을 비우고 서버 틱을 새 Zone 기준으로 센다. 외삽 기준 틱도 그 뒤의 스냅샷에서 다시 잡힌다.

## 옮기면서 고친 것
- 이전 이력은 관심 계산 주기를 별도 설정 `zone.interest_hz`로 두었다. 시야 수집과 어긋나면 낡은 관심 집합을 읽거나 버려지는 계산이 생긴다. 여기서는 스냅샷 주기 하나에 묶어 설정을 늘리지 않았다.
- 이전 이력은 병렬 실행기 주입(`set_parallel_executor`)을 함께 넣었다. 53에서 풀을 뺐고 위 측정으로도 필요 없어 옮기지 않았다.
- MP 변화가 관찰자 update를 만들던 것을 고쳤다(이전 이력에도 있던 낭비).
- 전투 이벤트를 관심 집합 대신 known으로 보낸다(51의 진입 분할 뒤 생긴 어긋남).
- 관심 계산 사이에 떠난 엔티티를 시야 수집에서 거른다. 이전 이력은 관심 집합에 남은 id가 다음 계산까지 시야에 걸려 있을 수 있었다.
- 뷰어가 샘플 하나인 엔티티를 멈춰 그리던 것을 고쳤다. dead reckoning에서는 spawn만 받은 채 걷는 엔티티가 흔하다.

## 검증
- C++: 테스트 299 → 307개 통과.
  - 단계 시간: 시계가 없으면 0, 주입하면 단계마다 정확히 잰다.
  - 직진은 한 번만 보고된다. 벽 미끄러짐은 이룬 속도를 보낸다. MP와 직선 투사체는 관찰자에게 알릴 일이 아니다.
  - 관심 계산은 시야 틱에만 하고, 계산 뒤 떠난 엔티티는 바로 despawn된다. 시야 주기 0은 거부한다.
  - 전투 이벤트는 대상을 아는 클라이언트에게만 가고, 공격자는 항상 받는다.
  - 봇 외삽.
  - 스냅샷 바이트 통계가 실제로 보낸 바이트와 같다.
  - 인코더 바이트 일치 테스트가 spawn 속도(-0.0 포함)까지 덮는다.
- dev·release·ASan, clang-tidy, clang-format 통과.
- 용량: 위 표.
- 로컬 end-to-end(smoke·fighters·looters·travelers): 통과.

# 26 Backend 리뷰 수정: Zone 인스턴스 하나, 재시도 순서, 빠진 정합성 테스트

## 배경과 목표
이 저장소는 먼저 만든 이력을 피처 단위로 다시 쌓으면서, 이미 옮긴 0~5단계 코드를 한 번 회고 리뷰했다([2026-10-20 회고 리뷰](../reviews/2026-10-20-retrospective.md)). 이 PR은 그중 Backend(.NET 모듈형 모놀리스: 인증, 캐릭터, WorldDirectory, Economy)와 마이그레이션 지적 B1~B13을 다룬다. 가장 큰 것은 [이슈 013](../issues/013-redeem-assigns-a-dead-zone-instance-after-restart.md)이다. Zone 프로세스를 재시작하고 15초 안에 들어온 캐릭터는 이미 죽은 옛 Zone 인스턴스를 소유자로 배정받아, 몬스터를 잡아도 보상이 모두 거절됐다. 완료 조건: 지적마다 코드로 확인하고 고치며, 고친 경우는 수정 전 코드에서 실패하는 테스트로 고정한다. 기본 프로필 직후 전투 프로필을 바로 돌리는 end-to-end가 통과한다.

용어: **lease**는 Zone·Gateway 프로세스가 주기적으로 갱신하는 "살아 있음" 기록이다(갱신 5초, 만료 15초). **Zone 인스턴스**는 Zone 프로세스 하나를 가리키는 ID로, 재시작하면 바뀐다. **소유권 세대(owner_epoch)**는 캐릭터가 입장할 때마다 오르는 번호다.

## 고민한 선택지와 결정
| 주제 | 선택지 | 결정 |
|---|---|---|
| Zone ID 하나에 살아 있는 인스턴스가 둘 | 배정만 최근 인스턴스로 / lease 만료를 줄임 / 새 등록이 옛 lease를 끝내고, 옛 인스턴스의 갱신을 거절 | 셋째. 배정만 바꾸면 옛 인스턴스를 가리키는 소유권 행이 15초 동안 지급을 받을 수 있다. 만료를 줄이면 갱신 부하가 늘고 잠깐의 정지에도 Zone을 잃는다 |
| 대신한 인스턴스 없이 lease만 놓친 Zone | 갱신 거절 / 허용 | 허용. 그 Zone ID에 프로세스가 그것 하나뿐이라, 거절하면 아무도 그 지역을 돌리지 않는다 |
| 지급할 때의 권한 | 소유권 행만 / 소유권 행과 Zone lease 생존 | 둘 다. lease가 끝난 Zone은 스스로 세션을 내보내지만, 그 전에 보낸 요청이 늦게 도착할 수 있다 |
| 재시도에 대한 답 | 권한을 먼저 보고 저장된 결과 / 저장된 결과를 먼저 | 저장된 결과를 먼저. 결과는 그때의 권한으로 정해졌다. 답을 잃은 사이 플레이어가 다시 입장하면 소유권 세대가 바뀌어, 권한을 먼저 보면 이미 지급된 처치를 "낡은 권한"으로 거절한다. Zone은 그 아이템을 바닥에 만들지 못하고 Backend에만 남는다. 처치는 기록한 Zone 인스턴스와 처치자가 같을 때만 반향한다 |
| 세션 경합에서 진 Redeem | 트랜잭션 전체 롤백 / savepoint까지 롤백하고 커밋 | savepoint. 티켓은 결과와 상관없이 한 번 쓰면 끝난다(ADR-0005). 전체를 되돌리면 진 티켓이 다시 쓸 수 있는 상태로 남는다 |
| 내부 gRPC 노출 | 지금 서비스 인증 / 기본 바인딩만 좁힘 | 바인딩만 좁힘(127.0.0.1). 호출자 인증은 인증서나 토큰 배포가 필요한 보안 단계의 일이다. 지금은 로컬 기본값이 모든 인터페이스에 열려 있어, 같은 네트워크의 누구나 처치 기록으로 재화를 만들 수 있는 것만 막는다 |
| 연결 문자열 기본값 | 개발용 값 / 빈 값 | 빈 값. 빼먹은 배포가 `change-me` 자격으로 뜨지 않고 시작 시 검증에서 멈춘다. 로컬 스크립트는 `.env`에서 만든다 |

## 리뷰에서 고친 것
| 지적 | 고친 것 |
|---|---|
| 재시작 직후 죽은 Zone 인스턴스가 배정된다(013), 만료된 lease가 갱신으로 되살아난다(B3) | lease 갱신이 성공하면 같은 트랜잭션에서 먼저 등록한 같은 Zone ID의 lease를 지금 끝낸다. 갱신 문장은 "나보다 늦게 등록한 같은 Zone ID 인스턴스가 없을 것"을 조건으로 건다. 배정은 최근 인스턴스부터 고른다 |
| 소유권 행만 맞으면 lease가 끝난 Zone도 지급받는다 | 처치·획득의 권한 확인이 Zone lease와 조인해 생존을 본다 |
| 드롭을 템플릿 허용 여부만 본다. 같은 아이템 1000개도 통과(B2) | 드롭 표가 아이템마다 둔 항목 수를 세어 그 수까지만 받는다(`DropTable.Accepts`) |
| 재입장 뒤의 재시도가 권한 확인에 걸려, Backend에만 있는 유령 아이템이 남는다(B6) | 처치는 영수증, 획득은 저장된 결과를 권한 확인보다 먼저 본다 |
| 세션 삽입 경합에서 지면 커밋 없이 끝나 티켓이 소비되지 않는다(B8) | 소유권 변경 직전에 savepoint를 두고, 지면 거기까지 되돌린 뒤 티켓 소비를 커밋한다 |
| 모르는 사용자 로그인이 해시와 검증을 둘 다 해 실제 계정보다 느리다. 주석은 "비슷한 시간"이라 한다(B9) | 처음 한 번 만든 더미 해시로 검증만 한다. 실제 계정과 같은 일이다 |
| 자산 조회 세 문장이 서로 다른 스냅샷을 본다(B12) | RepeatableRead 트랜잭션 하나에서 읽는다 |
| 설정 파일의 `Password=change-me`(B4), 내부 gRPC가 모든 인터페이스에서 듣는다(B1) | 빈 연결 문자열, gRPC는 127.0.0.1 |
| 목록의 시나리오가 그대로 시험되지 않는다(B5) | 아래 통합 테스트 9개와 드롭 표 단위 테스트 |
| 없는 uuid 도우미를 말하는 마이그레이션 주석, ADR-0005의 "UNIQUE INSERT" 표현(B13) | 주석을 실제에 맞췄다(주석만 바뀌고 DbUp은 스크립트 이름으로 기록하므로 적용된 DB에는 영향이 없다). ADR 본문은 두고 구현 메모를 덧붙였다 |

미룬 것: 캐릭터 생성의 클래스 검증(B7)은 콘텐츠 카탈로그가 Economy 모듈 안에 있어 공용으로 옮기는 일이 함께 필요하다. 코드로만 지키는 규칙의 DB 제약(B10)은 새 마이그레이션이 필요하다. 둘 다 규칙 정리 PR에서 한다. 계정 단위 로그인 시도 상한은 보안 단계에서 한다.

## 구현
- `Modules/WorldDirectory/WorldDirectoryRepository`: `RenewZoneLeaseSql`의 갱신 조건, 같은 트랜잭션의 `SupersedeOlderZonesSql`, 배정 `first_seen_at DESC`, Redeem의 savepoint `before_ownership`
- `Modules/Economy/ContentCatalog`: `DropTable(MonsterTemplateId, Gold, EntriesPerItem)`와 `Accepts`
- `Modules/Economy/EconomyRepository`: 권한 확인에 Zone lease 생존, 처치 영수증 선조회와 반향(`EchoKillAsync`), 획득의 저장 결과 선조회, 자산 조회 트랜잭션
- `Modules/Auth/AuthService`: 모르는 사용자용 더미 해시
- `appsettings.json`: 빈 연결 문자열, gRPC `127.0.0.1:5101`
- 테스트 하네스: `ApiClient.TicketForAsync`(이미 있는 캐릭터의 새 티켓), `Db.ExecuteAsync`(만료된 lease 같은 상태 준비), `Db.WaitForLockWaitAsync`(경합이 자리 잡을 때까지 대기)
- 문서: README의 자산·lease·검증·빌드 절, 통합 테스트 목록에 "Zone 재시작" 시나리오, 이슈 013 해결, 회고 리뷰의 B 처리, ADR-0005 구현 메모

## 만난 문제
- 처음 쓴 "같은 캐릭터의 티켓 두 장 동시 제출" 테스트는 수정 전 코드에서도 통과했다. 대부분 한쪽이 먼저 커밋해 뒤쪽이 존재 확인에서 지기 때문이다. 고친 경로(유니크 인덱스에서 지는 경우)는 타이밍이 맞을 때만 지나간다. 그래서 다른 Gateway의 세션 행을 커밋하지 않은 채 넣어 두고, Redeem이 그 인덱스에서 기다리는 것을 `pg_stat_activity`로 확인한 뒤 커밋하는 결정적 테스트로 바꿨다. 수정 전 코드에서 실패한다.
- [013](../issues/013-redeem-assigns-a-dead-zone-instance-after-restart.md): 원인과 해결은 이슈 문서에 있다.

## 검증
- .NET: 빌드 경고 0, `dotnet format` 통과. 단위 4 → 10, 통합 33 → 42 모두 통과.
- 수정 전 Backend 코드에 새 테스트를 돌리면 5개가 실패한다. Zone 재시작, lease가 끝난 Zone의 지급, 표보다 많은 드롭, 재입장 뒤 처치 재시도, 유니크 인덱스에서 진 Redeem이다. 나머지 새 테스트(같은 티켓 동시 제출, 만료 티켓, 같은 획득 요청 동시 두 개, lease만 놓친 Zone의 재갱신)는 원래 맞던 동작을 처음으로 시험한다.
- C++: 변경 없음.
- end-to-end를 lease 만료를 기다리지 않고 연달아 돌렸다. 기본: 봇 5개 전원 입장, 모순 0. 곧바로 전투: 처치 9(봇 집계), DB의 처치 영수증 10, Zone의 처치 거절 0. 수정 전에는 같은 순서에서 DB 영수증이 0이라 FAIL이었다([25](25-verification-harness.md)의 판정).

## 남긴 것
- Gateway의 lease 상실 처리(G5)와 Backend가 끝난 Gateway lease의 갱신을 거절하는 일은 함께 해야 한다. Backend만 거절하면 Gateway가 새 입장을 받지 못한 채 떠 있다. Gateway 수정 PR에서 한다.
- 컨테이너 배포(6단계)는 Backend gRPC 주소를 `Kestrel__Endpoints__Grpc__Url`로 바꿔야 한다. 내부 gRPC 호출자 인증은 보안 단계.
- B7, B10은 규칙 정리 PR.

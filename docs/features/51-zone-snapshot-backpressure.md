# 51 (8b) 스냅샷 역압: 링크별 예산, 오래 기다린 세션 우선, 시야 상한과 진입 분할

## 배경과 목표
이 프로젝트의 Zone(C++)은 100 ms마다 플레이어마다 스냅샷을 만들어 Gateway 링크로 보낸다. 스냅샷에는 "그 플레이어가 지난번 받은 뒤 시야 안에서 바뀐 것"이 담긴다. 용량 기준선([보고서 02](../reports/02-capacity-baseline.md))에서 한 지도에 봇 1,000명이 한꺼번에 들어오자 세 가지가 일어났다.
- 링크 큐가 1.1~1.2 GiB까지 자랐다.
- 틱을 57~59개 놓쳤다.
- 네 번 중 한 번은 Gateway가 밀려 생존 확인이 링크를 끊었다([이슈 020](../issues/020-overloaded-gateway-mistaken-for-a-dead-one.md)).

50(묶음 쓰기)만으로는 큐가 오히려 2.1 GiB로 커졌다. 보내는 쪽이 받는 쪽보다 빠르면 큐는 자란다.

이 PR은 큐 대신 흐름을 제어한다(ADR-0011). 설계는 상용 게임들의 방식을 참고해 이전 이력보다 바꿨다. 이전 이력은 수위를 넘으면 링크 전체를 멈췄다가 내려가면 재개했다. 지금은 링크별 예산 안에서 오래 기다린 세션을 먼저 보낸다. 같은 조건으로 다시 재서 보고서 03을 남긴다.

완료 조건:
- 밀릴 때 Zone은 스냅샷을 쌓지 않고, 미룬 세션도 상태를 잃지 않는다.
- 링크 큐는 예산 근처로 묶이고, 미룬 세션은 다음 틱에 먼저 받는다. 한 링크의 밀림이 다른 링크에 번지지 않는다.
- 1,000명 진입에서 놓친 틱과 메모리가 예산 안으로 돌아오고, 링크가 끊기지 않는다.

## 고민한 선택지와 결정
| 주제 | 선택지 | 결정 |
|---|---|---|
| 밀릴 때 스냅샷 | 큐에 쌓기 / 만든 뒤 버리기 / 만들기 전에 판단 | 만들기 전에 판단. 스냅샷은 상태라 옛 것은 다음 것보다 가치가 없다. 시야를 수집하지 않으면 그 변화는 다음 수집에 그대로 담긴다. 만든 뒤 버리면 직렬화 비용을 이미 치렀고, TCP 스트림에 들어간 바이트는 꺼낼 수 없다 |
| 판단 단위 | 링크 전체 정지·재개(두 수위, 이전 이력) / 링크별 예산 + 세션 순서 | 예산 + 세션 순서. 전체 정지는 모든 세션이 동시에 끊겼다 동시에 몰린다. 예산은 같은 상한을 지키면서 세션마다 고르게 늦춘다 |
| 세션 순서 | 고정(id) / 마지막 수신이 오래된 순 | 오래된 순. 이번에 못 받은 세션이 다음 틱에 맨 앞에 서서 굶는 세션이 없다. Unreal 리플리케이션의 "기다린 만큼 우선순위가 쌓이는" 방식과 같은 생각이다 |
| 시야 크기 | 제한 없음 / 가까운 N개 | 가까운 128개. 스냅샷 바이트가 N²에서 N × 128로 묶인다. 이미 보이는 대상은 히스테리시스 폭만큼 가깝게 쳐서 가장자리의 깜빡임을 막는다 |
| 진입 폭주 | 한 번에 / 스냅샷당 상한 | 스냅샷당 32개, 가까운 순. 군중에 들어온 플레이어가 수백 개의 생성을 한 번에 받지 않는다. 이슈 020의 직접 원인이다 |
| 잃으면 안 되는 메시지 | 예산에 포함 / 예외 | 예외. 명령 결과, 전투 사건, 인벤토리, 이전 통지는 지금처럼 바로 보낸다 |

## 구현
- `sim`
  - `MovementRules`에 `aoi_max_entities`·`aoi_max_spawns_per_view`(`game-data/rules/movement.toml`의 `[aoi] max_entities = 128`, `max_spawns_per_view = 32`, 검증 포함)
  - `RecomputeInterest`: 범위 안 후보를 거리로 순위를 매긴다. 이미 보이는 대상은 히스테리시스 폭만큼 앞당긴다. 상한까지만 남긴다(동점은 낮은 id).
  - `CollectView`: 새로 보인 엔티티를 가까운 순으로 상한까지만 생성으로 보낸다. 나머지는 알려주지 않은 채로 두어 다음 뷰에서 다시 고른다.
- `zone/server`
  - `LinkSink::QueuedBytes()`(GatewayLink는 50의 연결 값)
  - `ZoneHost::SendSnapshots`: 스냅샷 틱마다 세션을 링크별로 묶어 마지막 수신이 오래된 순으로 정렬한다. 링크 대기 바이트가 예산에 닿을 때까지 수집·인코딩·전송하고, 나머지는 `snapshots_deferred`로 센다.
  - 설정 `gateway_link.snapshot_budget_bytes`(4 MiB, 0은 거절)
  - 통계
    - `TickRunner`: 시뮬레이션과 호스트 전달 시간(`sim_us`·`host_us`)
    - 호스트 줄: 미룬 스냅샷, 링크 큐 최대 깊이, Gateway에서 다음 프레임이 오기까지의 최대 간격(`gateway_gap_max_ms`, 생존 확인 기한과의 거리)
- `scripts/bench/capacity.sh`: 위 통계를 측정 구간에 대해 요약한다(코어 수로 환산한 시간, 미룬 수, 큐 최대, 최대 간격).

## 옮기면서 고친 것
- 이전 이력은 링크 큐가 수위를 넘으면 그 링크의 모든 세션을 멈췄다. 링크별 예산 안에서 오래 기다린 세션부터 보내는 방식으로 바꿨다. 같은 상한을 지키면서 세션들이 동시에 멈췄다 몰리지 않는다. 테스트가 매 틱 한 자리만 날 때 세 세션이 차례로 받는 것을 확인한다.
- 진입 분할(스냅샷당 새 엔티티 상한)은 이전 이력에 없었다. 1,000명 진입 폭주가 이슈 020의 직접 원인이라 더했다.
- 이전 이력의 통계는 미룬 수와 큐 깊이까지만 남겼다. Gateway 프레임 사이의 최대 간격을 더해 생존 확인 기한과의 여유를 잴 수 있게 했다.
- 측정에서 장치를 하나씩 끈 비교(상한만, 예산만)를 더했다. 기본 설정에서 예산이 한 번도 발동하지 않았기 때문이다. 각 장치가 무엇을 맡았는지 숫자로 가렸다.

## 만난 문제
- 기본 설정으로 잰 1,000명에서 예산이 한 번도 발동하지 않았다(미룬 스냅샷 0, 링크 큐 최대 4.16 MB < 예산 4.19 MB). 개선이 상한 덕분인지 예산 덕분인지 가를 수 없었다. 시야 상한을 끈 실행과 예산을 끈 실행을 따로 했다(보고서 03 "장치별 효과").

  - 놓친 틱 57~59 → 0

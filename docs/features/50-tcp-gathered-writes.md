# 50 (8b) 묶음 쓰기와 송신 대기 바이트

## 배경과 목표
이 프로젝트의 모든 TCP 전송(클라이언트 TCP·WebSocket, Gateway↔Zone 링크)은 `TcpByteStream` 하나를 쓴다. 이 클래스가 읽기 루프와 순서 있는 쓰기 큐, 닫기를 맡는다. 용량 기준선([보고서 02](../reports/02-capacity-baseline.md))에서 한 지도에 봇 1,000명이면 Zone A의 링크 송신 큐가 1.1~1.2 GiB까지 자랐다. 이 큐는 프레임마다 쓰기를 하나씩 걸었고, 쌓인 양을 위에서 볼 방법도 없었다.

8b(송신 역압)의 첫 PR이다. 전송층에 두 가지를 넣는다.
- 쓰는 비용을 줄인다.
- 쌓인 양을 위층이 읽을 수 있게 한다.

이 신호로 Zone이 스냅샷을 미루는 일은 다음 PR(51)이 한다.

완료 조건:
- 쓰기가 진행 중일 때 들어온 프레임은 다음에 한 번의 scatter-gather 쓰기로 나간다. 순서는 그대로다.
- `QueuedBytes()`가 "받았지만 커널이 아직 가져가지 않은 바이트"를 정확히 센다. 닫기는 남은 것을 보내고, 중단은 버린다.

## 고민한 선택지와 결정
| 주제 | 선택지 | 결정 |
|---|---|---|
| 모으는 방식 | 큰 버퍼 하나에 복사 / 프레임 버퍼를 그대로 scatter-gather | scatter-gather. 복사 없이 프레임 벡터들을 버퍼 목록으로 넘긴다 |
| 모으는 시점 | 타이머로 모았다 보내기 / 쓰기가 끝날 때 쌓인 것 전부 | 쓰기가 끝날 때. 지연을 더하지 않는다. 쓰기가 비어 있으면 첫 프레임은 바로 나간다 |
| 대기량 신호 | 프레임 수 / 바이트 | 바이트. 스냅샷 크기는 시야에 따라 수십 배 차이 난다 |
| 노출 위치 | `TcpByteStream`만 / `MessageConnection` 인터페이스까지 | 인터페이스까지. TCP 프레이밍과 WebSocket이 같은 값을 준다 |

## 구현
- `TcpByteStream`
  - 쓰기 큐를 대기분(`pending_`)과 진행 중(`in_flight_`)으로 나눈다. 쓰기가 끝나면 대기분 전부를 한 번의 `async_write`(버퍼 목록)로 보낸다.
  - `QueuedBytes()`: 쓴 만큼 줄고, 닫히면 0이다.
- `MessageConnection::QueuedBytes()`와 `FramedConnection`·`WebSocketConnection`의 구현.
- 테스트 3개
  - 바이트 계산과 순서
  - 소켓 버퍼보다 큰 500프레임이 묶여서도 순서대로 도착하는지
  - 중단 시 버리고 0

## 옮기면서 고친 것
- 이 저장소의 `TcpByteStream`에는 이전 이력에 없던 닫기 대기 상한(linger)과 "송신만 먼저 끊기"가 있다. 묶음 쓰기는 그 흐름을 그대로 두고 쓰기 큐만 바꿨다. 쓰기가 비면 송신을 끊는 조건은 "진행 중인 쓰기가 없을 때"로 같다.

## 검증
- C++: 테스트 285 → 288개 통과. 시간에 기대는 전송 테스트를 30번 반복해도 통과. dev·release·ASan, clang-tidy, clang-format 통과.
- 로컬 end-to-end(smoke·fighters·looters·travelers): 통과.
- 용량(`scripts/bench/capacity.sh`, release, 보고서 02와 같은 조건)

  | 1,000명 | 기준선(보고서 02) | 이 PR |
  |---|---|---|
  | 놓친 틱 | 57~59 | 31~43 |
  | Zone A CPU | 0.70 | 0.86~0.87 |
  | Zone A 메모리 | 1.1~1.2 GiB | 1.7~2.1 GiB |
  | Gateway CPU / 메모리 | 0.72 / 111~118 MiB | 0.67~0.69 / 64~65 MiB |

  500명은 변화가 없다(Zone·Gateway 각 0.25~0.27코어, 놓친 틱 0).
- 해석: 쓰기 시스템 호출이 줄어 Zone이 틱을 덜 놓친다. 그만큼 스냅샷을 더 많이 만든다. 하지만 Gateway가 받아 가는 속도는 거의 그대로다. 상한 없는 링크 큐가 오히려 더 커졌다. 묶음 쓰기만으로는 부족하고, 큐가 수위를 넘으면 스냅샷을 미루는 짝이 필요하다(51). 이 PR의 `QueuedBytes()`가 그 신호다.

# 01 전송 계층: TCP, WebSocket, UDP

## 배경

이 프로젝트는 MMORPG 서버다. 게임 클라이언트는 **Gateway**라는 접속 프로세스에 연결하고, Gateway는 메시지를 지역 시뮬레이션 프로세스인 **Zone**으로 넘긴다. 계정·캐릭터·자산은 **Backend**(C#)가 PostgreSQL로 관리한다. 메시지는 모두 Protobuf로 정의되어 있고, 클라이언트는 20 Hz로 이동 입력을 보내며 서버는 10 Hz로 주변 상태 스냅샷을 보낸다. 이 글은 그 메시지를 **어떤 전송 위에 실을지**에 대한 결정이다.

## 결론

| 구간 | 선택 | 한 줄 이유 |
|---|---|---|
| 게임 클라이언트 ↔ Gateway | 길이 프리픽스 TCP + Protobuf | 네이티브 클라이언트의 관례이고, 나중에 UDP로 갈 길을 막지 않는다 |
| 브라우저 뷰어 ↔ Gateway | WebSocket (별도 포트, 같은 Protobuf) | 브라우저는 raw TCP를 열 수 없다 |
| Gateway ↔ Zone | 세션 다중화 영구 TCP | 초당 수천 메시지가 오가는 핫 패스. HTTP/2 프레이밍 비용을 낼 이유가 없다 |
| Zone·Gateway ↔ Backend | gRPC | 호출 빈도가 낮고 deadline·취소·타입 있는 스텁이 중요하다 |
| 클라이언트 ↔ Backend | HTTPS JSON | 로그인·캐릭터 선택은 요청 수가 적다 |

"길이 프리픽스 TCP"란 각 메시지 앞에 4바이트 길이를 붙여 보내는 가장 단순한 프레이밍이다. TCP는 바이트 스트림이라 메시지 경계가 없으므로 경계를 직접 만들어야 한다.

## WebSocket을 게임 링크로 쓰지 않은 이유

WebSocket은 TCP 위에 HTTP 업그레이드 핸드셰이크, 2~14바이트 프레임 헤더, 클라이언트→서버 방향의 바이트별 XOR 마스킹을 얹은 것이다. 얻는 것은 브라우저 접속과 HTTP 인프라(Ingress, 프록시, 443 포트) 통과다. 잃는 것은 세 가지다.

1. 서버가 수신 바이트마다 마스킹을 풀어야 한다. 비용은 작지만 0이 아니다.
2. HTTP 파서 의존성이 생긴다.
3. **UDP로 전환할 수 없다.** WebSocket은 TCP 전용이다.

세 번째가 결정적이다. TCP는 "초기 개발과 디버깅을 단순하게 하기 위한 선택"이고, 패킷 손실 지연을 측정한 뒤 이동·스냅샷을 UDP로 옮길지 정한다. 그 선택지를 열어 두려면 전송 계층이 프레이밍·메시지 의미와 분리되어 있어야 한다.

## 그래서 코드는 이렇게 나뉜다

```
TcpByteStream          소켓 하나: 읽기 루프, 순서 보장 쓰기 큐, 종료 알림
  ├─ FramedConnection      길이 프리픽스 프레임   (네이티브 클라이언트, 내부 링크)
  └─ WebSocketConnection   RFC 6455 프레임        (브라우저 뷰어)
         └─ 둘 다 MessageConnection 인터페이스로 세션에 전달
```

세션 상태 머신(`SessionProtocol`)은 "Protobuf 메시지가 들어오고 나간다"만 알고 어느 전송인지 모른다. 그래서 Gateway는 리스너 두 개를 열고 소켓을 각자의 전송으로 감싼 뒤 **같은 세션 로직**에 넘긴다. 전송 두 개가 한 프로토콜을 공유한다는 사실 자체가 "전송과 의미를 분리했다"는 증거다. UDP 전송이 들어오면 바뀌는 것도 이 어댑터 하나다.

## gRPC 스트리밍을 게임 링크에 쓰지 않은 이유

HTTP/2 흐름 제어와 헤더 압축은 RPC에는 좋지만 10~20 Hz로 흐르는 스냅샷에는 맞지 않는다. 또 gRPC는 유실 시 재전송하는 TCP 위에서만 동작하므로 UDP 전환 문제가 WebSocket과 같다. Backend 호출처럼 빈도가 낮고 "2초 안에 답이 없으면 실패"라는 deadline이 중요한 곳에만 쓴다.

## UDP로 가면 무엇이 바뀌나

- 바뀌지 않는 것: 메시지 정의, 서버 권위(최종 판단은 서버), 입력 순번, 스냅샷 델타 구조, 세션 상태 머신.
- 바뀌는 것: 전송 어댑터, 그리고 "유실돼도 다음 패킷이 상태를 복원하도록" 메시지를 보내는 방식. 핵심은 재전송하지 않는 것이다. 이동 입력은 최근 N개를 중복 포함해 보내고, 스냅샷은 클라이언트가 마지막으로 확인한 번호 기준으로 델타를 만든다.
- 추가되는 것: 반드시 도착해야 하는 메시지(아이템 획득, 스킬 결과, 거래)를 위한 신뢰 채널. 순번과 ack 비트마스크로 미확인 메시지만 재전송하거나, TCP를 병행한다.

유실이 화면에 어떻게 보이는지, 틱 레이트가 어디에 영향을 주는지는 [02 UDP 유실 보정과 틱 레이트](02-udp-loss-and-tick-rate.md)에서 따로 다룬다. 이 글의 결론만 필요하다면 거기까지 읽지 않아도 된다.

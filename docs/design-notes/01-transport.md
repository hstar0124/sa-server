# 01 전송 계층: TCP, WebSocket, UDP

## 결론

| 구간 | 선택 | 한 줄 이유 |
|---|---|---|
| 게임 클라이언트 ↔ Gateway | 길이 프리픽스 TCP + Protobuf | 네이티브 클라이언트의 관례이고, 나중에 UDP로 갈 길을 막지 않는다 |
| 브라우저 뷰어 ↔ Gateway | WebSocket 어댑터 (3b) | 브라우저는 raw TCP를 열 수 없다 |
| Gateway ↔ Zone | 세션 다중화 영구 TCP | 핫 패스. HTTP/2 프레이밍 비용을 낼 이유가 없다 |
| Zone·Gateway ↔ Backend | gRPC | deadline, 취소, 타입 있는 스텁. 호출 빈도가 낮다 |
| 클라이언트 ↔ Backend | HTTPS JSON | 로그인·캐릭터 선택은 요청 수가 적다 |

## WebSocket을 게임 링크로 쓰지 않은 이유

WebSocket은 TCP 위에 HTTP 업그레이드 핸드셰이크, 2~14바이트 프레임 헤더, 클라이언트→서버 방향의 바이트별 XOR 마스킹을 얹은 것이다. 얻는 것은 브라우저 접속과 HTTP 인프라(Ingress, 프록시, 443 포트) 통과다. 잃는 것은 세 가지다.

1. 서버가 수신 바이트마다 마스킹을 풀어야 한다. 비용은 작지만 0이 아니다.
2. HTTP 파서 의존성이 생긴다.
3. **UDP로 전환할 수 없다.** WebSocket은 TCP 전용이다.

세 번째가 결정적이다. 설계 문서 6.1절은 TCP를 "초기 개발과 디버깅을 단순하게 하기 위한 선택"으로 두고, 패킷 손실 지연을 측정한 뒤 이동·스냅샷을 UDP로 옮길지 결정한다고 했다. 이 선택지를 열어 두려면 전송 계층이 프레이밍·메시지 의미와 분리되어 있어야 한다. 그래서 `FramedConnection`은 바이트와 프레임만 알고, 세션 상태 머신은 전송을 모른다. UDP 전송이 들어오면 바뀌는 것은 전송 어댑터 하나다.

브라우저 뷰어는 WebSocket이 필수이므로 같은 Protobuf 페이로드를 싣는 어댑터로 붙인다. 전송 두 개가 한 프로토콜을 공유하는 구조 자체가 "전송과 의미를 분리했다"는 증거가 된다.

## gRPC 스트리밍을 게임 링크에 쓰지 않은 이유

HTTP/2 흐름 제어와 헤더 압축은 RPC에는 좋지만 20 Hz 스냅샷에는 맞지 않는다. 또 gRPC는 유실 시 재전송하는 TCP 위에서만 동작하므로 UDP 전환 문제가 WebSocket과 같다. 내부 Backend 호출처럼 빈도가 낮고 deadline이 중요한 곳에만 쓴다.

## UDP로 가면 무엇이 바뀌나

- 바뀌지 않는 것: 메시지 정의, 서버 권위, 입력 순번, 스냅샷 델타 구조, 세션 상태 머신.
- 바뀌는 것: 전송 어댑터, 그리고 "유실돼도 다음 패킷이 상태를 복원하도록" 메시지를 보내는 방식. 자세한 내용은 [02 UDP 유실 보정과 틱 레이트](02-udp-loss-and-tick-rate.md).
- 추가되는 것: 반드시 도착해야 하는 메시지(획득, 스킬 결과, 거래)를 위한 신뢰 채널. 순번 + ack 비트마스크로 미확인 메시지만 재전송하거나, TCP를 병행한다.

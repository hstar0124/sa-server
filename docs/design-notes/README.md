# 설계 노트

"왜 이렇게 만들었는지"를 주제별로 설명하는 글이다. **각 글은 그것만 읽어도 이해되도록** 서두에 필요한 배경을 담았다. 수치는 측정 전까지 설계 가정이며, 측정 결과는 `docs/reports/`에 따로 남긴다.

| 노트 | 답하는 질문 |
|---|---|
| [01 전송 계층: TCP, WebSocket, UDP](01-transport.md) | 왜 클라이언트 링크가 WebSocket이 아니라 TCP인가. UDP로 가면 무엇이 바뀌나 |
| [02 UDP 유실 보정과 틱 레이트](02-udp-loss-and-tick-rate.md) | 패킷이 사라지면 화면이 끊기나. 20 Hz가 어디에 영향을 주나 |
| [03 밀집 전투의 확장성](03-dense-combat.md) | 보스전·길드전처럼 한 곳에 몰리면 무엇이 먼저 터지고 어떻게 막나 |
| [04 입장 경로와 소유권](04-entry-and-ownership.md) | 티켓 한 장, 세션 하나, 소유 Zone 하나를 어떻게 보장하나 |
| [05 순수 시뮬레이션 코어](05-pure-simulation.md) | Zone 로직이 소켓·시계·난수를 모르게 만든 이유와 얻은 것 |
| [06 전투](06-combat.md) | 스킬 검증 순서, 투사체 터널링, 몬스터 AI, 생명주기당 한 번의 사망, 이벤트 전달 |
| [07 자산과 멱등성](07-economy-consistency.md) | 드롭·획득에서 Zone과 Backend의 역할, 동시 획득·요청 중복·응답 유실·낡은 Zone을 어떻게 막나 |

| [09 킬 랭킹과 Redis](09-ranking-redis.md) | 왜 "내 순위"만 Redis로 옮겼고, 복사본이 비거나 뒤처져도 답이 틀리지 않게 하는 방법 |
| [10 두 번째 Zone과 소유권 이전](10-zone-transfer.md) | 캐릭터를 다른 Zone으로 옮길 때 소유자를 하나로 유지하고, 응답 유실·늦은 Zone·죽은 도착 Zone을 어떻게 다루나 |
| [11 밀림을 다루는 방법](11-flow-control.md) | 보내는 쪽이 받는 쪽보다 빠를 때 왜 큐로 받으면 안 되나, 상용 게임은 어떻게 막나, 예산·우선순위·시야 상한이 각각 무엇을 바꿨나 |

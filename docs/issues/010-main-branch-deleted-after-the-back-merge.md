# 010 되돌리기 PR을 병합한 직후 main 브랜치가 지워짐

- 상태: 해결 (main을 v0.2.0 커밋에 되살리고 룰셋 시행을 다시 켬, 2026-10-19)
- 발견: 0.2.0 릴리스 절차를 마친 뒤 확인하다, 2026-10-19
- 영향: 원격에 `main`이 없다. 태그 `v0.2.0`과 커밋은 남아 있어 내용 손실은 없다. 하지만 다음 릴리스 PR이 들어갈 브랜치가 없다. 같은 원인으로 그동안 `main`·`develop`에 PR 필수와 CI 필수 조건도 시행되지 않았다

## 증상
릴리스 절차를 마친 뒤 확인하니 원격에 `main`이 없었다. 태그는 PR #21의 병합 커밋 `0dbec6d`를 가리킨다.

```
$ git ls-remote origin refs/heads/main
(출력 없음)
$ gh api repos/hstar0124/sa-server/branches/main
{"message":"Branch not found", ...}
```

## 원인 분석
- 저장소의 "병합 후 머리 브랜치 자동 삭제"는 꺼져 있다(`delete_branch_on_merge=false`). 자동 삭제가 아니다.
- PR #22(머리 `main` → `develop`, 릴리스 표기 되돌리기)의 이벤트를 보면, 05:32:11에 병합되고 5초 뒤 05:32:16에 같은 계정으로 `head_ref_deleted`가 찍혔다. 병합 직후 PR 화면의 "Delete branch" 버튼으로 머리 브랜치가 지워진 것이다. 피처 브랜치를 정리할 때 쓰는 그 버튼이다. 0.1.0의 같은 되돌리기 PR #12에는 이 이벤트가 없다.
- 룰셋 `protect-main-branch`는 `main`과 `develop`을 대상으로 삭제 금지, 강제 푸시 금지, PR 필수, 필수 검사 다섯 개를 담고 있다. 그런데 시행 상태가 `disabled`였다. 삭제 금지가 시행 중이었다면 버튼은 실패했을 것이다.
- 룰셋을 언제 왜 껐는지는 API로 알 수 없다. 마지막 수정은 2026-10-15다. 저장소가 비공개였던 동안에는 무료 계정이라 룰셋이 시행되지 않았을 것이다([009](009-actions-minutes-exhausted-on-a-private-repo.md)에서 공개로 바꿨다).

## 원인
되돌리기 PR은 머리가 `main`이라 병합 화면에 "Delete branch"가 뜨고, 피처 PR처럼 눌렀다. 그것을 막아야 할 룰셋은 꺼져 있었다. 절차 문서에도 "되돌리기 PR 뒤에는 머리 브랜치를 지우지 않는다"는 말이 없었다.

## 해결
- `main`을 `0dbec6d`(태그 `v0.2.0`의 커밋이자 PR #21의 병합 커밋)로 다시 만들었다. PR #22는 `main`을 `develop`에 합치는 쪽이라 그 뒤로 `main` 자체는 바뀌지 않았다. 그래서 이 커밋이 정확한 머리다.
- 룰셋 시행 상태를 Active로 바꿨다. 이제 `main`·`develop`은 삭제와 강제 푸시가 막히고, PR과 CI 다섯 잡 통과가 필수다.
- 되돌리기를 릴리스 브랜치 → `develop`으로 바꾸는 방법도 있었다. 그러면 위험한 버튼이 뜨지 않는다. 하지만 `main`의 병합 커밋과 태그가 `develop`에서 닿지 않게 된다. 그래서 `main` → `develop`을 유지하고 규칙과 삭제 금지로 막기로 했다.

## 재발 방지
- CONTRIBUTING.md 릴리스 항목: 되돌리기 PR(머리 `main`)을 병합한 뒤 "Delete branch"를 누르지 않는다. 룰셋이 시행 중이면 GitHub이 거절한다. 릴리스 마지막에 원격 `main`의 머리가 태그 커밋과 같은지 확인한다.
- CONTRIBUTING.md 브랜치 항목: 룰셋은 시행 상태 Active여야 하고, 삭제 금지와 필수 검사 다섯 잡을 담는다고 적었다.

# 014 릴리스 태그 v0.3.0이 이전 저장소의 커밋으로 올라감

- 상태: 해결 (태그와 Release를 다시 만듦, 2026-10-21)
- 발견: 0.3.0 릴리스를 마친 뒤 원격 `main`과 태그를 대조하다, 2026-10-21
- 영향: 다시 만들 때까지 태그 `v0.3.0`과 GitHub Release가 이 저장소 이력에 없는 커밋을 가리켰다. Release의 소스 묶음이 이전 저장소의 코드였다. `main`·`develop`과 PR은 영향이 없다

## 증상
릴리스 절차의 마지막 확인에서 원격 `main`의 머리와 태그 커밋이 달랐다.

```
$ git ls-remote origin refs/heads/main 'refs/tags/v0.3.0^{}'
1d346af...	refs/heads/main
8fad5eb...	refs/tags/v0.3.0^{}
```

`8fad5eb`는 `Merge branch 'release/0.3.0'`이라는 커밋이고, `develop`에서도 닿지 않는다. 태그 메시지는 이 저장소에서 쓴 적 없는 영어 문장이었다.

## 원인 분석
- 이 저장소는 이전에 만든 이력을 피처 단위로 다시 옮겨 만든다. 작업용 클론에 이전 저장소를 원격 `old`로 붙여 두고 커밋을 참고해 왔다.
- `git fetch old`는 기본으로 태그도 가져온다. 그래서 작업용 클론에 이전 저장소의 `v0.3.0`~`v0.9.0`이 로컬 태그로 있었다.
- 릴리스 절차의 `git tag -a v0.3.0 origin/main`은 같은 이름의 태그가 있어 실패했다(`already exists`). 이어진 `git push origin v0.3.0`은 그 로컬 태그, 곧 이전 저장소의 태그를 올렸다. 태그 객체와 함께 그 커밋에 닿는 이전 이력도 원격으로 갔다.
- `gh release create v0.3.0`은 원격에 이미 있는 태그로 Release를 만들었다.

## 원인
작업용 클론에 다른 저장소의 태그가 같은 이름으로 섞여 있었고, 절차는 태그 생성이 실패해도 멈추지 않고 푸시로 넘어갔다.

## 해결
- `gh release delete v0.3.0 --cleanup-tag`로 Release와 원격 태그를 지우고, `1d346af`(PR #38의 병합 커밋)에 태그를 다시 만들어 푸시한 뒤 같은 노트로 Release를 다시 게시했다. 태그 커밋이 원격 `main`의 머리와 같음을 확인했다.
- 작업용 클론에서 이전 저장소의 태그를 지우고, `old` 원격은 태그를 가져오지 않게 했다(`remote.old.tagOpt=--no-tags`).
- 원격에 잠시 올라간 이전 이력의 객체는 어느 참조에서도 닿지 않아 GitHub의 정리 대상이 된다. 이 저장소의 브랜치와 태그에는 남지 않는다.

## 재발 방지
- 릴리스 전에 작업용 클론의 `git tag -l`에 만들 태그가 없는지 본다.
- 태그 생성과 푸시를 `&&`로 묶어, 생성이 실패하면 푸시하지 않는다.
- 릴리스 마지막의 "원격 `main` 머리 = 태그 커밋" 확인(이슈 010)이 이번 문제를 잡았다. 그대로 둔다.

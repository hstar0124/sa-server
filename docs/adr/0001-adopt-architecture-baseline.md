# ADR-0001: Server_Architecture.md v1.0을 설계 기준으로 채택

- 상태: Accepted
- 날짜: 2026-10-12

## 맥락
`docs/Server_Architecture.md`(v1.0, 2026-10-08)는 구현 전 설계 문서다. 불변 조건(부록 B), 멱등성·조건부 UPDATE(10~11절), owner_epoch·lease fencing(14절), Outbox/Inbox(12절)는 검토 결과 수정 없이 채택 가능하다. 반면 장비 전제(17절)와 구현 순서(20절) 일부는 실제 장비와 포트폴리오 목적에 맞게 조정이 필요하다.

## 결정
- 문서의 **불변 조건, 데이터 소유권 표(5절), 트랜잭션 규칙, fencing 규칙, 검증 시나리오(21절)**를 구현 사양으로 채택한다.
- 문서와 ADR이 충돌하면 ADR이 우선한다. 문서 본문은 구현 완료 후 실측값으로 갱신한다.
- 조정 사항은 각각 별도 ADR(0002~0008)로 기록한다.

## 결과
- 설계의 "왜"는 문서에, "무엇을 바꿨나"는 ADR에 남아 리뷰어가 추적할 수 있다.
- 문서를 수시로 고치지 않으므로 문서와 코드가 어긋날 위험이 있다. 각 단계 완료 시 문서 갱신을 완료 조건에 포함한다.

### 2026-10-16 보정: 설계 문서를 README와 테스트 목록으로 흡수하고 제거
- 상태: 위 결정을 이렇게 바꾼다(Accepted).
- 원 설계 문서는 구현 전 가정(장비·파티션 계획, 1단계 K3s, Redis 티켓·presence, 메모리 예산 등)이 섞여 있어 이미 여러 ADR로 뒤집혔고, 그대로 두면 읽는 사람이 어느 쪽이 현재 방향인지 매번 대조해야 한다.
- 현재 구현과 일치하는 내용만 옮긴다. README에는 **그때까지 만든 것**만 적고, 단계가 끝날 때마다 그 단계의 구조·흐름·측정을 더한다. 아직 만들지 않은 부분의 방향은 해당 단계의 ADR과 피처 문서가 다룬다. 지금 README에는 전체 구조, 데이터의 기준, 네트워크와 입장, Zone 틱, 소유권과 lease가 들어가고, 정합성 시나리오 표는 **`tests/integration/README.md`**로, 지표 목록은 **`observability/README.md`**로 간다.
- 코드·문서의 "설계 문서 N절" 참조는 위 자리를 가리키게 고친다. `docs/Server_Architecture.md`는 저장소에서 제거한다.
- 원칙은 그대로다. 결정이 바뀌면 ADR, README는 현재 방향의 요약이다.

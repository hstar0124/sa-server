# ADR-0002: 개발 순서, compose 개발 루프, K3s 도입 시점, 디스크 레이아웃 유지

- 상태: Accepted
- 날짜: 2026-10-12

## 맥락
문서 20절은 1단계에 K3s·PG·로그·메트릭을 모두 넣고 봇/부하 도구를 10단계에 둔다. 실제 장비는 문서 17.2절의 파티션 계획과 다르다(root 100G, /var/lib/docker 500G, /home 322G, swap 8G, SELinux disabled). XFS는 축소가 불가능하므로 계획대로 가려면 재설치가 필요하다. 프로젝트는 포트폴리오 용도이며 K3s 운용 자체가 보여줄 항목이다.

## 결정
1. **디스크를 재설치하지 않는다.** 데이터 볼륨은 Docker 기본 경로(`/var/lib/docker`, 500 GiB LV)를 사용한다. 문서 17.2절은 폐기한다.
2. **개발 루프는 docker compose**(`deploy/compose/`). 모든 단계의 완료 조건은 먼저 compose 위에서 통과한다.
3. **K3s는 6단계(Outbox·Kafka·Worker)부터 도입**한다. 상태 있는 서비스가 셋 이상 되는 시점이며, 이후 8단계 소유권 이전과 10단계 장애·부하 테스트는 K3s 위에서 시연한다. "compose에서 통과한 테스트가 K3s에서도 통과"가 10단계 완료 조건이다.
4. **봇 클라이언트는 2단계에 만든다**(ADR-0006). 통합 테스트 하네스는 1단계에 만든다.
5. 단계: 0 골격·툴체인 → 1 Backend 인증·마이그레이션·테스트 하네스 → 2 Zone 시뮬레이션·봇·뷰어 → 3 Gateway·티켓 → 4 전투 → 5 자산·멱등성 → 6 Outbox·Kafka·K3s → 7 Redis → 8 두 번째 Zone·이전 → 9 거래 → 10 부하·장애·백업·보고서.

첫 세로 단면은 문서와 같다: 로그인 → 이동 → 몬스터 처치 → 획득 → 재접속 후 보유 확인(5단계 완료 시점).

### 2026-10-12 보정: 2단계와 3단계의 경계
2단계 완료 조건 "봇 두 개가 서로를 보고 시야 진입·이탈"은 **순수 시뮬레이션과 프로세스 내 봇**으로 검증한다(`zone_sim` 테스트, `zone_server`의 `[dev] local_bots`). 네트워크 봇 클라이언트(`tools/loadgen/client`)와 2D 뷰어·WebSocket 어댑터는 Gateway 입장 경로(티켓, Gateway↔Zone 라우팅)가 생기는 **3단계**로 옮긴다. 입장 경로 없이 봇을 접속시키려면 임시 무인증 경로가 필요한데, 그런 코드는 만들지 않는다. 봇 두뇌(`sa::bot`)는 2단계에 만들어 두 경로가 같은 두뇌를 쓴다.

### 2026-10-12 보정: 3단계 범위
3단계는 입장 경로(서명 티켓 → RedeemEntryTicket → Gateway↔Zone 링크), 프로세스 lease, 네트워크 봇 클라이언트와 `scripts/e2e-local.sh`로 끝낸다. **2D 뷰어와 WebSocket 어댑터는 3b**로 분리해 다음에 한다. 입장 경로가 먼저 검증되어야 뷰어가 붙을 대상이 생기기 때문이다.

## 결과
- 게임이 돌아가기 전에 인프라에 시간을 쓰지 않는다. 장애 원인이 인프라인지 코드인지 분리된다.
- K3s 매니페스트가 늦게 생기므로, compose 설정을 쓸 때 환경 변수·포트·볼륨을 K3s로 옮기기 쉬운 형태(12-factor)로 유지한다.
- swap 8 GiB는 K3s 도입 시 `--kubelet-arg=fail-swap-on=false` 또는 swapoff로 처리한다. 그때 결정한다.

## 대안
- 문서대로 1단계 K3s: 정합성 증명에 기여 없이 메모리 1 GiB 이상과 디버깅 간접화를 선불한다. 기각.
- 재설치·전용 PV: 데이터 삭제 수반, 성능 격리 효과 없음(같은 NVMe). 기각.

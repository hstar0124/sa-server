# ADR-0013: 거래는 Backend가 협상 상태를 소유하고, Zone은 검증과 중계만 한다

- 상태: Accepted
- 날짜: 2026-10-23

## 맥락
두 캐릭터의 거래는 제안을 주고받다가 **둘 다 같은 제안에 동의한 순간** 양쪽의 아이템과 금화가 한 번에 바뀌어야 한다. 어느 쪽도 손해를 보거나 두 번 받아서는 안 된다. 이 프로젝트의 자산은 Backend의 PostgreSQL이 기준이다. 획득은 "Zone이 메모리에서 예약하고 Backend 트랜잭션이 확정한다"는 길을 냈다(설계 노트 07). 정해야 할 것은 두 가지다.
- 협상(제안, 수정, 동의) 상태가 어디에 사는가
- 클라이언트의 거래 메시지가 어느 길로 Backend에 닿는가

## 결정
1. **협상 상태는 Backend의 테이블이다.**
   - `trades`: 거래 ID, 참여자 둘, 상태, 버전, 양쪽 금액, 양쪽이 동의한 버전, 만료 시각
   - `trade_participants`: 열린 거래에 참여 중인 캐릭터. (world, character)가 기본 키
   - `trade_items`: 거래에 올라간 아이템. 아이템 ID가 기본 키

   제안이 바뀌면 버전이 오르고 양쪽 동의가 모두 지워진다. 동의는 버전을 가리킨다. Zone은 거래 상태를 기억하지 않는다. 세션이 거래 중인지 표시하는 비트 하나만 든다.
2. **DB 제약이 규칙을 지킨다.**
   - 한 캐릭터는 열린 거래 하나: `trade_participants` 기본 키
   - 한 아이템은 열린 거래 하나: `trade_items` 기본 키
   - 참여자는 서로 다른 둘, 금액은 음수 불가, 동의는 거래가 가졌던 버전만: CHECK
   - 잔액 차감: 조건부 UPDATE(`balance >= amount`)

   참여·아이템 행은 거래가 닫힐 때 지워져 다음 거래를 막지 않는다.
3. **확정은 트랜잭션 하나다.** 양쪽이 같은 버전에 동의하는 순간, 같은 트랜잭션에서 다음을 한다.
   1. 거래 행을 `FOR UPDATE`로 잡는다.
   2. 두 캐릭터가 모두 호출한 Zone 인스턴스와 소유권 세대의 소유인지 확인한다. 둘이 그 Zone에 있어야 Zone의 거리 검증이 의미가 있고, 낡은 소유자는 막힌다.
   3. 두 인벤토리를 캐릭터 ID 오름차순으로 잠근다.
   4. 올라간 아이템이 여전히 제안자 소유인지 확인한다.
   5. 양쪽 칸이 "지금 칸 − 내보내는 것 + 받는 것 ≤ 용량"을 만족하는지 본다.
   6. 금화를 조건부 UPDATE로 차감·가산한다.
   7. 아이템을 두 번에 걸쳐 옮긴다. 먼저 받는 쪽으로 옮기되 칸 번호를 그 인벤토리의 용량 이상(주차 칸)으로 둔다. 그다음 받는 쪽의 빈 칸에 낮은 번호부터 앉힌다. 한 번에 옮기면, 둘 다 가득 찬 인벤토리끼리 하나씩 맞바꿀 때 "칸 하나에 아이템 하나" 유일 인덱스가 중간 상태에 걸린다. 주차 칸이 용량 이상이라 칸 번호 음수 금지 CHECK도 그대로 둔다.
   8. 인벤토리 버전을 올리고, 원장(`item_transferred`, `currency_debit`, `currency_credit`, 사유 `trade`)과 양쪽의 `TradeCompleted` Outbox 이벤트를 쓴다.
   9. 거래를 `completed`로 바꾸고 참여·아이템 행을 지운다.

   어느 하나가 실패하면 전부 되돌리고, 거래는 열린 채 양쪽 동의를 지운 뒤 사유를 돌려준다.
4. **모든 RPC는 멱등이다.** `request_id`로 `command_results`(scope `trade`)에 행을 확보한다. 재시도는 저장된 결과를, 같은 ID의 다른 본문은 `REQUEST_MISMATCH`를 받는다. 획득과 같은 규칙이다. `request_id`는 Zone이 (캐릭터, 소유권 세대, 클라이언트 요청 id)의 HMAC digest로 만든다. 다른 세션이나 다른 캐릭터의 요청 id와 겹치지 않는다(획득의 이슈 012와 같은 방식).
5. **길은 클라이언트 → Gateway → Zone → Backend다.**
   - Zone 시뮬레이션이 자기만 아는 것을 검증한다. 살아 있는가, 이동(ChangeZone) 중이 아닌가, 열기의 상대가 `economy.toml`의 `trade.range_m` 안에 있는 플레이어인가.
   - 통과하면 `Pending` 결과를 주고 호스트 요청을 낸다.
   - 호스트가 Backend를 부른다(공용 재시도 정책). 응답으로 요청자에게 `CommandResult`를, **두 참여자에게 `TradeUpdate`**(상태, 버전, 양쪽 제안, 동의 여부)를 보낸다.
   - 확정되면 양쪽의 자산을 다시 읽어 `InventoryUpdate`로 보낸다.
6. **세션이 끝나면 Zone이 취소를 요청한다.** 이유는 가리지 않는다. 접속 종료, 추방, Gateway 링크 끊김, 무응답·느린 클라이언트 끊기, 지역 이동이 모두 해당한다. 그때 호스트가 `CancelTrade`(캐릭터의 열린 거래 전부)를 부른다. 그래도 놓친 거래는 Backend의 만료(`Trading:ExpirySeconds`, 마지막 변경 뒤 60 s)가 다음 조작 때 닫는다. 별도 청소 작업은 두지 않는다.
7. **World 간 거래는 없다.**

## 결과
- 거래 중 어느 프로세스가 죽어도 상태는 DB에 있다. Zone이 재시작해도 거래를 잃지 않는다. 두 참여자 중 하나가 다른 Zone으로 가면 확정은 `COUNTERPARTY_NOT_HERE`로 거절되고, 세션 종료가 취소를 부른다.
- 매 조작이 RPC 한 번이다. 제안 수정이 잦으면 RPC도 잦다. 거래는 초당 수 건이라 문제가 아니고, 측정이 다르면 그때 Zone 메모리 협상을 검토한다.
- 조회 모델은 `trades_completed`를 얻는다(마이그레이션 0009, 소비자 델타).
- 통합 테스트: 양쪽 자산 보존, 동시 동의의 단일 확정, 같은 아이템을 두 거래에 올리기 거절, 금액 부족·칸 부족 거절, 낡은 Zone 거절, 재시도 멱등, 한 명 이탈 시 취소, 가득 찬 인벤토리끼리의 맞교환.

## 대안
- **Zone 메모리 협상 + Backend 확정 한 번:** 기각. RPC는 적지만 Zone이 죽으면 협상이 사라진다. "한 캐릭터는 거래 하나"를 Zone 두 개 사이에서 지킬 수 없다(두 Zone의 두 캐릭터가 같은 세 번째 캐릭터와 열 수 있음). DB 제약으로 지키려면 결국 Backend에 행이 필요하다.
- **클라이언트가 Backend HTTP로 직접 거래:** 기각. 거리 검증을 Zone이 못 하고 클라이언트 좌표를 믿어야 한다.
- **주차 칸을 음수로(이전 이력):** 기각. 칸 번호 음수 금지 CHECK를 풀어야 한다. 용량 이상의 번호는 같은 효과를 내면서 제약을 그대로 둔다.
- **칸 유일성을 지연 가능한 제약으로:** 기각. 부분 유일 인덱스는 지연할 수 없어 배타 제약으로 바꿔야 하고, 그러면 위반 오류 코드가 바뀌어 획득 경로의 처리도 바뀐다.
- **우편·경매장:** 범위 밖. 다음.

# ADR-0009: Redis는 측정된 병목에만 쓴다 (7단계 범위)

- 상태: Accepted
- 날짜: 2026-10-22

## 맥락
설계 기준은 Redis 용도로 넷을 든다. 입장 티켓 캐시, 캐릭터가 어느 Zone에 있는지(presence), Zone 조회 캐시, 랭킹 Sorted Set이다. 7단계에 넷을 다 넣을지 정해야 했다. 이 프로젝트에서 구성 요소를 넣는 근거는 "쓸 줄 안다"가 아니라 "이 병목 때문에 넣었고 이만큼 나아졌다"여야 한다(작업 규칙: 측정 없는 캐시·큐·인덱스는 넣지 않는다).

기준선(보고서 01, PostgreSQL만): 상위 20명은 캐릭터 100만에서도 p99 2.35 ms로 규모와 무관했다. 반면 한 캐릭터의 순위는 앞선 행을 세므로 캐릭터 수에 비례했다. 10만에서 615 req/s, 100만에서 62 req/s였다.

## 결정
1. **랭킹의 "내 순위"만 Redis Sorted Set으로 옮긴다.** ZREVRANK는 캐릭터 수에 로그로 비례한다. 상위 N명은 PostgreSQL로도 충분했지만, 같은 키에서 함께 읽는다.
2. **티켓 캐시는 넣지 않는다.** 티켓은 HMAC 서명이라 Gateway가 로컬에서 검증하고, DB는 소비할 때 한 번 본다. 병목이 없다.
3. **presence와 Zone 조회 캐시는 그것을 자주 묻는 기능이 생길 때 넣는다.** 지금은 "이 캐릭터가 어디 있나"를 초당 수천 번 묻는 기능(채팅, 친구 목록, Zone 간 메시지)이 없다. 생기면 같은 방법(기준선 → 도입 → 재측정)으로 정한다.
4. **Redis는 복사본이다.** 기준은 통계 조회 모델(`character_projections`)이다. 지속성을 끄고, 메모리 상한과 `noeviction`을 둔다. 꽉 차면 조용히 버리지 않고 쓰기 오류가 난다. EventWorker가 시작할 때, 키가 없을 때, 쓰기가 실패했을 때 조회 모델에서 다시 채운다.
5. **Redis가 없거나 비어도 답은 맞다.** Backend는 키나 멤버가 없거나 Redis에 닿지 않으면 PostgreSQL로 답한다. `Rankings:Backend=Postgres`로 설정만 바꾸면 PostgreSQL로 돌아간다.

## 결과
- 들인 뒤 같은 도구와 조건으로 다시 잰 결과는 보고서 01에 있다.
- 설계 기준의 Redis 용도 표는 "후보"로 읽는다. 각 행은 자기 측정 보고서가 생길 때 구현된다.
- Redis와 조회 모델은 한 트랜잭션이 아니다. 그 틈은 위 4의 다시 채우기와 5의 대체로 메운다.

## 대안
- 네 용도를 모두 구현: 잴 부하가 없는 캐시 셋이 생기고, 왜 있는지 설명할 수 없다. 기각.
- PostgreSQL에 순위 열을 두고 주기적으로 갱신: 갱신 비용이 캐릭터 수에 비례하고, 신선도가 주기에 묶인다. 기각.
